## Scope and result

This audit inspected every tracked `.svg` blob present in four pinned local
Git trees. It did not modify, install in, build, fetch, clean, or otherwise run
project tooling in those repositories. The audit used pinned-commit exports,
so a working-tree edit cannot enter a corpus result.

The result supports TFSB20's lifecycle direction but rejects full-corpus v0.2
support. All four corpora exceed the 128-selected-SVG contract, and none of the
four complete trees passes the current schema-1 parser unchanged. The failures
are expected profile or accessibility-boundary mismatches, not v0.2
regressions. Terminal Nova remains the authoritative supported release fixture.

## Reproducible method

`tools/audit-dogfood-corpus.mjs` is a Node ESM audit tool, not product code. It
has no dogfood-path default, performs no network access, walks without following
symlinks, processes one SVG at a time, emits no source content, bounds samples
to five relative paths per failure class, and omits timestamps, elapsed time,
host data, and input paths from deterministic output. `tsconfig.tools.json`
checks its JSDoc types. Vitest covers deterministic ordering, collision
classification, failure aggregation, bounded samples, and absence of absolute
input paths.

The reproducible sequence is:

1. Find repositories by matching `remote.origin.url`, not directory basename.
2. Capture `git status --porcelain=v2 --branch --untracked-files=all`, origin,
   revision, branch/detached state, and shallow state.
3. Count tracked blobs and SVG bytes with `git ls-tree -r -l <revision>`.
4. Run `git archive --format=tar --output=<scratch>/<corpus>.tar <revision>`
   and extract it outside the checkout. Assert that export SVG count and bytes
   equal the direct Git-tree values.
5. Run `npm run build`, then invoke `npm run audit:dogfood -- --corpus <json>`
   for each export. Each JSON argument supplies a corpus ID, export path,
   recorded Git metadata, and direct tree totals; the path is consumed but not
   emitted.
6. Compare two independently written JSON and Markdown outputs byte for byte.
7. Repeat each dogfood Git status command and compare it with the before
   snapshot.

The final two full runs produced the same summary digest shown above. The
package `files` allowlist contains only `dist`, `NOTICE`, and
`COMMERCIAL-LICENSE.md`; `tools/`, its tests, and this evidence are not in the
npm payload.

No complete-path portable collision was present, but the zero result does not
remove the v0.1 portable-name guard. A synthetic NFC/case collision remains a
required failure scenario.

## XML, SVG, and accessibility profile

The machine summary records every element name, every attribute name by
element, namespace counts, root-attribute value families, paint families,
transform functions, markup, local/external references, active-content
signals, and file-level feature prevalence. The inventory parser is independent
of schema 1, so a schema failure does not hide later elements in the same file.

Evidence-ranked profile observations include:

- Lucide uses paths in 2,184 files, circles in 508, rectangles in 468, defs in
  47, clipping in 31, gradients in 23, and transforms in 43 occurrences. Root
  presentation attributes such as `fill`, `stroke`, line caps/joins, width,
  and height are common.
- Every Simple Icons SVG contains one path, a title, `role="img"`, `viewBox`,
  and no `desc`. Schema 1 requires title and desc with IDs plus exact
  `aria-labelledby`, so all 3,453 stop at `XML_INVALID_STRUCTURE`.
- Every Tabler SVG contains paths; 225 files contain `<use>`, 225 contain
  rectangles, and the outline/filled split dominates identity collisions.
  Root `fill`, stroke presentation, class/style, and non-schema namespaces are
  the leading parser boundaries.
- theSVG uses paths in 12,411 files, groups in 3,133, rectangles in 1,860,
  defs in 1,593, linear gradients in 953, clip paths in 395, styles in 352,
  radial gradients in 168, and masks in 104. It contains 16 external
  references, 21 files with DOCTYPE declarations, one processing instruction,
  two CDATA-bearing files, and current-parser active-content failures in 11
  files (product `XML_ACTIVE_CONTENT` rejects `<style>`, `<image>`, `<animate>`,
  and inline `on*`/`style` attributes; `profile.activeContent` inventories narrow
  script/foreignObject/embedding tags). None of those unsafe markup classes is
  proposed for support.

## Lifecycle scale and memory

Because zero external files genuinely parse, the summary truthfully reports
zero projected canonical/provenance/manifest records for these untransformed
trees. It does not pretend that unsupported SVG can become canonical TOML.

For scale planning only, the ten-file Terminal Nova production fixture measured
37,748 canonical asset-TOML bytes, approximately 5,830 provenance bytes, 2,082
manifest bytes, 1,360 full machine-result bytes, 42,756 preview bytes, and a
40,754-byte store-only bundle. Linear extrapolation of that *Terminal Nova
shape* gives the following non-acceptance estimates:

| Assets | Asset TOML | Provenance | Full result | Single-page preview |
| ---: | ---: | ---: | ---: | ---: |
| 10 | 36.9 KiB | 5.7 KiB | 1.3 KiB | 41.8 KiB |
| 100 | 368.6 KiB | 56.2 KiB | 11.9 KiB | about 0.4 MiB |
| 1,000 | 3.6 MiB | 561.5 KiB | 117.3 KiB | about 4.1 MiB |
| 12,457 | about 44.8 MiB | about 6.8 MiB | about 1.4 MiB | about 50 MiB |

Actual profile-expanded TOML could differ substantially. These figures exist
only to evaluate architecture shape.

Observed local Node 22.22.2 audit timings were 0.69 s Lucide, 0.60 s Simple
Icons, 1.79 s Tabler, and 2.24 s theSVG. Maximum resident size was about 81,
78, 407, and 114 MiB respectively. Tabler's 2.8 MiB generated preview SVG is
the outlier; a direct current-parser probe of that one file peaked at about
152 MiB. Per-file streaming therefore prevents whole-corpus accumulation but
does not make DOM expansion free.

Two `fflate@0.8.3` store-only proxies bound bundle memory:

- 128 entries totaling exactly 32 MiB completed in 0.08 s with about 112 MiB
  maximum resident size and a 33,567,510-byte ZIP.
- 12,457 entries totaling 28,183,953 bytes completed in 0.10 s with about
  135 MiB maximum resident size and a 30,002,697-byte ZIP, before a TFSB
  manifest and canonical model were added.

The second result shows that ZIP construction alone is not the blocker. Full
corpus lifecycle planning, profile incompatibility, identity, preview, and
output contracts remain unresolved. Likely v0.2 operations on the supported
128-asset boundary are sub-second to a few seconds on similar local hardware,
with staging/fsync dominating mutation. No full-corpus runtime claim is made.

## Terminal architecture decisions

### A. Scale and limits

Retain the v0.1/v0.2 1,024-archive-entry, 128-selected-SVG,
8-MiB-per-entry, and 32-MiB aggregate limits. Do not add configurable increases
or batching. A v0.2 canonical mutation plan supports at most 128 assets; a
larger hand-authored project may be inspected only by commands whose contract
does not create a complete next tree. Full-corpus import/reconcile is not a
v0.2 goal. Operators may construct deterministic, legally reviewed shards
outside TFSB.

### B. Nested identity

Retain basename-derived identity for unmanifested v0.2 import/reconcile. The
existing opt-in TFSB bundle manifest remains authoritative for its explicit
asset IDs after byte and collision validation. Third-party nested collections
may use exact selectors to choose one collision-free subset, but two selected
paths that derive the same ID cannot coexist. Normalized path IDs,
`--strip-prefix`, mapping files, and collection prefixes are deferred together
to avoid prematurely choosing ergonomics from four schema-incompatible
corpora. No opaque hash ID is permitted.

### C. Read-only compatibility analysis

Do not add `tfsb analyze` in v0.2. Its useful limits, ZIP-versus-directory
authority, per-file detail channel, and profile diagnostics belong with the
v0.3 profile decision. This committed audit helper and versioned JSON summary
are the repeatable bridge. The helper is not installed, exported, or presented
as a product command.

### D. Whole-project transaction

Keep complete planning before mutation. At the supported boundary, parse files
sequentially, hold the bounded normalized plan and rendered next tree, stage a
complete sibling `.tfsb`, reparse it, revalidate the snapshot under the
existing lock, and swap once. No batch may publish canonical state. A count or
aggregate-size breach fails before staging. Projects above the mutation bound
receive a stable resource diagnostic rather than partial work.

### E. Bundle construction

Keep pinned in-memory `zipSync` store-only construction and the existing
count/size ceilings. The measured 32 MiB boundary is viable without a new
dependency or streaming writer. Whole-corpus bundles are unsupported; a
selected 128-asset shard is the v0.2 scale contract. Temporary-file output,
manifest-first/two-pass streaming, and higher ceilings are deferred.

### F. Preview

Keep one generated `index.html`, one CSS file, per-asset files, no script, and
no server. Add native `loading="lazy"` and `decoding="async"` to gallery images.
Ten and 100 assets are supported; 1,000 and each measured full corpus exceed
the 128-asset refusal. Chunking, per-asset pages, search metadata, and client
JavaScript are unnecessary in v0.2.

### G. Human and machine output

Versioned machine JSON for valid read-only project operations remains complete
and untruncated, including thousands of records from a larger hand-authored
v0.1 project. Human output may summarize with an exact total, exact omitted
count, and selectors or `--json` guidance. v0.2 adds neither NDJSON nor a
detailed-output side file. A mutation, bundle, or preview above its supported
bound fails with aggregate counts; it does not emit a partial authoritative
record list.

### H. SVG profile

Keep schema 1 unchanged. None of the external corpora is directly importable,
and that is expected. No root-presentation, shape, accessibility, namespace,
gradient, style, `<use>`, XML-version, declaration, processing-instruction, or
active-content support is added in TFSB20A.

## v0.3 evidence backlog

1. Decide whether schema accessibility can represent title-only `role="img"`
   inputs without weakening explicit accessible-name ownership; Simple Icons
   supplies 3,453 examples.
2. Model root presentation and basic shapes deliberately; Lucide and Tabler
   provide the highest file prevalence.
3. Define `<use>`, referenced groups/paths, and symbol-like reuse; Tabler has
   225 files and 26,857 `<use>` occurrences.
4. Design gradient, clipping, masking, opacity, style/class, and transform
   boundaries; theSVG supplies the broadest combined evidence.
5. Decide opt-in path-derived identity, strip prefix, collection prefix, and
   explicit mapping/manifest precedence together; Tabler and theSVG are the
   primary collision corpora.
6. Design a bounded compatibility-analysis product contract, including ZIP
   snapshot authority, aggregate versus detailed output, and count/memory
   ceilings.
7. Keep DOCTYPE/entity, unsafe declarations, processing instructions,
   external references, and active content fail-closed unless a separate
   security decision proves a narrower inert representation.

## Required scenario dispositions

1. Terminal Nova remains unchanged as the fully supported release contract.
2. Flat thousands are measured by Simple Icons and exceed v0.2 count limits.
3. Nested variants are measured by Tabler and theSVG and fail on collisions.
4. A cross-directory rename is never inferred; `--rename` remains explicit.
5. theSVG is the primary mostly-unsupported profile inventory.
6. Companion/legal candidates are counted and bounded; only explicitly selected
   allowed companions can enter a TFSB project.
7. A human-edited canonical subset reconciles only against a collision-free,
   bounded shard; the larger upstream is separate audit evidence.
8. A selected shard can bundle; a whole measured corpus cannot.
9. Preview supports 10 and 100, refuses 1,000 and full-corpus counts.
10. Read-only machine results at thousands of canonical records are full and
    may be multi-megabyte; mutation/bundle/preview limit failures are aggregate.
11. NFC/case portable-name collision remains a deterministic validation error.
12. A dirty dogfood checkout is isolated by `git archive <revision>`; current
    snapshots happened to be clean.
13. No dogfood SVG or legal document is copied into this repository.
14. Any audit or lifecycle failure leaves dogfood checkouts untouched and
    leaves TFSB canonical state unmutated; only an explicitly requested report
    output may be created by the audit tool.

## Legal and provenance boundary

Lucide records ISC terms plus MIT terms for listed Feather-derived icons and a
separate brand-logo statement. Simple Icons records CC0 for the project while
its disclaimer expressly warns that individual icons may have different
licenses and that trademark/brand permissions remain the user's
responsibility. Tabler records MIT terms. theSVG records MIT for its codebase
and separate `LEGAL.md`, `TRADEMARK.md`, and `DISCLAIMER.md` statements that
individual brand rights and per-icon terms remain external.

These are repository-document observations, not legal advice. Parsing success
would not grant redistribution or trademark rights. All four are appropriate
for local read-only dogfood. No future fixture may be copied until the exact
asset, upstream provenance, license/attribution, trademark constraints, and
repository redistribution purpose receive explicit review.
