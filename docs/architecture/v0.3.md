# Theme Forge Stellar Burst v0.3 Common SVG Compatibility Architecture

- Status: proposed for v0.3 implementation
- Release target: `@knowledge-forge-ai/theme-forge-stellar-burst@0.3.0`
- Predecessor: accepted immutable v0.2.0 lifecycle release
- Profile identifier: `tfsb-svg-common-v0.3`
- Model schema: 2
- Mutation boundary: unchanged at 128 selected assets
- Evidence: [compatibility projection](../evaluations/v0.3-compatibility-projection.md)
- Decisions: [ADR 0005](../decisions/0005-schema-2-accessibility-and-presentation.md),
  [ADR 0006](../decisions/0006-productized-analyze-and-normalization.md), and
  [ADR 0007](../decisions/0007-migration-and-provenance-compatibility.md)

## Purpose and release boundary

v0.3 productizes read-only SVG compatibility analysis and adds a closed,
human-oriented schema for common icon SVGs. It owns explicit accessibility
authority, document presentation, common basic geometry, bounded transforms
and local references, reviewable import normalization, deterministic schema
migration, and legally reviewed collision-free dogfood shards.

The accepted v0.2.0 lifecycle remains intact. Schema 1 and its released SVG,
TOML, digest, provenance, reconciliation, bundle, diff, format, preview, and
transaction contracts do not change. The archive limits and 128-asset mutation
boundary do not increase.

v0.3 is not a full icon warehouse lifecycle, collection identity design,
directory import/reconcile workflow, raw XML/CSS language, Studio protocol, or
attempt to accept every construct in theSVG. Parsing and profile compatibility
do not convey license, trademark, attribution, or redistribution permission.

## Preserved invariants

1. Unknown TOML and SVG fields fail closed.
2. Unsafe content is rejected before normalization and is never silently
   stripped.
3. Canonical state changes only through an explicit complete transaction.
4. Ordinary commands never migrate schema or infer accessibility intent.
5. Source paths remain project-relative or normalized archive entries; reports
   never expose absolute paths or source text.
6. Network access is absent from runtime analysis, import, migration, build,
   install, reconciliation, bundle, diff, format, and preview.
7. Identity, profile compatibility, lifecycle scale, and legal permission are
   independent acceptance dimensions.

## Closed v0.3 SVG profile

| Surface | Accepted in schema 2 | Explicitly outside v0.3 |
| --- | --- | --- |
| Accessibility | `labelled`, `decorative`, `consumer_labelled` | inferred labels, filename labels, ambiguous missing intent |
| Artwork | path, group, use, circle, ellipse, rect, line, polyline, polygon | raw nodes, symbol, text/tspan, pattern |
| Definitions | linear gradient, typed path/shape/group definitions | radial gradient, clipping, mask, filter, marker, symbol |
| Paint | `none`, six-digit hex, `currentColor`, typed local linear gradient with optional six-digit fallback (`url(#ID) #RRGGBB` in canonical SVG) | named CSS colors, rgb/hsl functions, CSS variables, external paint URLs |
| Presentation | fill, stroke, widths/joins/caps/miter, opacity, fill/stroke opacity, fill/clip rule | style strings, class selectors, arbitrary property bags, external stylesheets |
| Transforms | ordered translate, scale, rotate records | matrix, skewX, skewY, arbitrary transform text in schema 2 |
| References | resolved asset-local use of typed definitions; local xlink input may normalize | external URLs, data URLs, reference cycles, symbol sprites |
| XML | XML 1.0 UTF-8, default SVG namespace, comments, text-only metadata, optional canonical declaration; no version attribute emitted on canonical root | DOCTYPE/entity, PI other than the leading XML declaration, CDATA, unknown namespaces |
| Active content | none | script, style, image, foreignObject, event attributes, animation, external resources |

`clip-rule` is a typed presentation property even though `<clipPath>` is not a
v0.3 element. It preserves common author intent on paths and shapes and avoids
conflating a fill-rule-like property with support for clipping trees.

`color` is deferred. The measured common Lucide, Simple Icons, and Tabler
sources do not require a document `color` value; `currentColor` deliberately
remains consumer-resolved. A later typed `color` decision must not introduce a
CSS variable or arbitrary property escape hatch.

## Schema-version architecture

### Homogeneous projects and dispatch

Both `.tfsb/project.toml` and every `.tfsb/assets/*.toml` declare the same
`schema_version`. A project is entirely schema 1 or entirely schema 2. Mixed
projects fail with `SCHEMA_PROJECT_VERSION_MISMATCH` before planning.

Each version has its own closed parser and writer. Schema-1 functions remain
frozen. Schema-2 decoding produces version-discriminated validated values and
then a common semantic interface used by build, install, check, list,
reconcile, bundle, diff, format, and preview. Version-specific features remain
typed variants; callers do not receive raw objects or generic attribute maps.

Existing projects retain their version. Import into an existing project uses
that project version. A new project created by v0.3 defaults to schema 2 and
reports the choice; `--schema 1` remains available for a schema-1-compatible
new import. Selecting schema 2 is not migration because no canonical project
exists yet. No command selects a schema by guessing from the first SVG.

Future schema 3 adds a new decoder/writer and explicit migration edge. It does
not redirect schema-1 or schema-2 serializers, digest bases, or provenance
readers.

### Independent version domains

Project schema, provenance schema, bundle-manifest schema, build-receipt
version, CLI JSON envelope version, analyzer aggregate schema, and analyzer
detail schema are independent. A project-schema change does not force an
unrelated envelope version. An incompatible shape change in any domain bumps
only that domain.

## Accessibility ownership

### Canonical modes and SVG output

| Mode | Required TOML | Canonical root | Child accessibility nodes |
| --- | --- | --- | --- |
| `labelled` | non-empty `title`; optional non-empty `description`; optional `focusable` | `role="img"`, exact `aria-labelledby`, optional `focusable="false"` / `focusable="true"` matching declared value | title with ID; optional desc with ID |
| `decorative` | no title or description; optional `focusable` | `aria-hidden="true"`, optional `focusable="false"` / `focusable="true"`; no role | none |
| `consumer_labelled` | no title or description; optional `focusable` | `role="img"`, optional `focusable="false"` / `focusable="true"`; no `aria-hidden`, `aria-label`, or `aria-labelledby` | none |

`consumer_labelled` is the one canonical name. It is deliberately distinct
from decorative: the SVG remains exposed as an image, but its standalone file
has no accessible name. An inline host must add `aria-label` or
`aria-labelledby`; an HTML `<img>` host must provide meaningful `alt`.
Decorative `<img>` use still requires `alt=""` on the HTML element because an
inner SVG `aria-hidden` is not advertised as sufficient HTML accessibility.

Generated IDs are `tfsb-<asset-id>-title` and
`tfsb-<asset-id>-description`. They are stable and checked against every local
ID. Explicit IDs are retained during schema-1 migration and may be supplied in
schema 2 only when locally unique. The serializer never generates a title,
description, or label from filename, asset ID, source path, corpus metadata, or
brand name.

### Import classification

- A title plus optional description becomes `labelled` only under explicit
  exact-common normalization when IDs or references must be generated.
- A source already matching the labelled contract needs no accessibility
  normalization.
- `aria-hidden="true"` with no labels may become `decorative` under explicit
  authority. Labels plus `aria-hidden` are conflicting intent and require an
  entry-specific map; labels are never silently discarded.
- An unlabeled source requires a normalization-map decision of `decorative` or
  `consumer_labelled`. Neither is inferred from corpus, filename, or element
  prevalence.

Preview displays the declared mode. It may display title/description only for
`labelled`; for the other modes it shows fixed status text, never synthesized
accessible content. Diff reports `accessibility.mode`, title, description, and
explicit ID changes separately.

## Document presentation and inheritance

Schema 2 places root presentation in a dedicated table:

```toml
[presentation]
fill = "none"
stroke = "currentColor"
stroke_width = 2
stroke_linecap = "round"
stroke_linejoin = "round"
```

Schema 2 preserves schema-1 canvas and element presentation fields:
`[canvas] shape_rendering` (`auto` | `optimizeSpeed` | `crispEdges` |
`geometricPrecision`), `aria_hidden` boolean on groups and elements, and
`fill_fallback` / `stroke_fallback` for gradient fallback paint. Element and
group records use the same field names as explicit overrides. Absence means
inherit for fill, stroke, stroke width, line cap, line join, miter limit, fill
opacity, stroke opacity, fill rule, and clip rule. `none` is an explicit paint
value, not absence. `opacity` does not inherit; it applies at the declared
root, group, or element and nested opacity composites multiply as SVG
rendering requires.

Schema-2 local gradient paint uses `fill_gradient = "gradient-id"` or
`stroke_gradient = "gradient-id"`, with optional `fill_fallback` /
`stroke_fallback`, mutually exclusive with the corresponding paint field.
Schema 2 does not accept `url(#...)` strings in TOML. The schema-1 writer
retains its released spelling. Both canonical SVG writers serialize fallback
paint as `url(#VALID_LOCAL_ID) #RRGGBB` with exactly one ASCII space. Analyzer
value classification applies XML attribute normalization, trims surrounding
attribute whitespace, and then accepts only that separator and fallback shape;
it does not broaden `url(...)` generally.

Import promotes supported root attributes into `[presentation]` and records the
typed normalization identifier `promote_root_presentation`. Normalization facts
are data, not warning/info diagnostics: the released `MachineDiagnostic`
severity remains the closed value `error`.

The schema-2 SVG serializer must reuse or delegate every shared element and
definition to the frozen schema-1 rendering helpers. The shared presentation
order remains `fill`, `stroke`, `stroke-width`, `stroke-linecap`,
`stroke-linejoin`, `stroke-miterlimit`, `opacity`, `aria-hidden`; schema-2-only
`fill-opacity`, `stroke-opacity`, `fill-rule`, and `clip-rule` follow that
shared block and precede `transform`. Root presentation follows the same order
after the schema-specific canvas/accessibility attributes.

Element order is type-specific, not one generic presentation/transform/geometry
rule:

- a shared path emits `id`, shared presentation, schema-2-only presentation,
  `transform`, then `d`;
- a shared use emits `id`, `href`, `x`, `y`, shared presentation,
  schema-2-only presentation, then `transform`;
- a shared group emits `id`, shared presentation, schema-2-only presentation,
  `transform`, then children; and
- schema-2-only geometry emits `id`, shared and schema-2-only presentation,
  `transform`, then its type-specific geometry fields.

When no schema-2-only fields are present, these rules reproduce the exact
schema-1 bytes. In particular, `<use>` does not use a generic `id`,
presentation, transform, geometry order.

Semantic diff locations use `presentation.<field>` for root declarations and
`elements[<stable-key>].presentation.<field>` for overrides. Inherited
effective values may be shown as context but do not replace declaration-level
diffs.

## Common basic geometry

| Type | Required normalized fields | Constraints | Canonical SVG |
| --- | --- | --- | --- |
| circle | `cx`, `cy`, `r` | finite; `r > 0` | `<circle cx cy r>` |
| ellipse | `cx`, `cy`, `rx`, `ry` | finite; both radii `> 0` | `<ellipse cx cy rx ry>` |
| rect | `x`, `y`, `width`, `height`; optional typed corners | finite; width/height `> 0`; radii non-negative and bounded by SVG semantics | `<rect x y width height rx ry>` |
| line | `x1`, `y1`, `x2`, `y2` | finite | `<line x1 y1 x2 y2>` |
| polyline | `points` | at least two finite pairs | `<polyline points="x,y ...">` |
| polygon | `points` | at least three finite pairs | `<polygon points="x,y ...">` |

SVG-default coordinates may normalize to explicit zero and are reported as an
exact-semantic normalization. Rect `rx` without `ry` (or the inverse) becomes
`corner_radius`; unequal values become `corner_radii = [rx, ry]`. The canonical
SVG emits both `rx` and `ry` when rounded corners are present.

Every primitive accepts the closed presentation override, optional locally
unique ID, and typed transform list. Shapes in definitions may be referenced
by local use. Preview renders primitives directly. Diff compares type and
typed numeric fields. Migration does not create primitives because schema 1
has no primitive to recover; it retains existing paths.

The [Lucide example](../examples/v0.3/lucide-consumer-labelled.toml) and
[Tabler example](../examples/v0.3/tabler-decorative.toml) show that ordinary
records remain shorter and clearer than equivalent XML.

## Transforms, groups, and references

Schema 2 uses ordered typed records:

```toml
transforms = [
  { type = "translate", x = 2, y = 1 },
  { type = "rotate", angle = 45, cx = 12, cy = 12 },
  { type = "scale", x = 0.5, y = 0.5 },
]
```

Translate permits omitted `y = 0`; scale permits omitted `y = x`; rotate
permits no pivot or both `cx` and `cy`. Partial pivots, non-finite values,
matrix, skewX, skewY, and unparsed transform strings fail. Operation order is
semantic and preserved.

Schema 2 replaces the schema-1 path-or-use group body with a bounded typed
`children` array. A child is one supported artwork variant; depth is at most
eight and the entire asset has at most 1,024 modeled elements. Empty groups
fail. This supports common mixed groups without a DOM fragment escape hatch.

`use.reference` names one ID in typed definitions. Import accepts local
`href="#id"` and may normalize local `xlink:href` plus its standard namespace
to SVG 2 `href`. The graph must resolve, remain acyclic, and terminate in typed
paths/shapes/groups. External references, references to artwork nodes,
`<symbol>`, and definition-order ambiguity fail. Canonical definitions precede
artwork. Shared schema-1 definitions emit in category order: linear gradients,
definition groups, then definition paths. Each category preserves normalized
model array order; IDs are never a sorting key. Schema-2-only definition
primitives follow the shared categories in their documented type order and
also preserve normalized array order.

For newly imported schema-2 source, `canonicalize_definition_order` may move
definitions into the canonical category model while preserving source-relative
order within each resulting category. The normalized model retains that order.
The contract never claims both source-order preservation and ID sorting.

The measured Tabler `<symbol>/<use>` sprite files do not motivate symbol
support: they are warehouse artifacts with embedded style and exceed the
individual-icon import goal. The 6,184 individual outline/filled files do not
need symbols.

## XML, namespaces, and security boundary

### Accepted inert syntax

- UTF-8 XML 1.0 with an optional one leading declaration;
- one unprefixed SVG root in the default SVG namespace;
- SVG `version="1.1"`, `version="1.0"`, or omission, canonicalized to standard SVG root output (no `version` attribute is emitted on canonical SVG output);
- comments, which are inventoried and discarded as non-semantic;
- schema-1-compatible text-only metadata; and
- the xlink namespace only when every xlink use is an asset-local reference
  that an approved normalization converts to SVG 2 `href`.

### Unsupported inert syntax

Processing instructions other than the leading declaration, CDATA, unknown
namespaces, structured RDF metadata, text/tspan, clip paths, masks, radial
gradients, filters, markers, patterns, symbols, named CSS colors, arbitrary
attributes, and unsupported transforms are `unsupported`. They are not
silently stripped or flattened.

### Unsafe syntax

DOCTYPE/entity declarations, script, style elements or attributes, inline
`on*`, image, foreignObject, animation, external/data/protocol-relative URLs,
external stylesheets, and active embedded objects are `unsafe`. Inventory marks
unsafe independently of parser order. Normalization cannot downgrade unsafe to
unsupported or supported.

An unknown construct fails even when the browser might ignore it. A namespace
or declaration is accepted only under the exact inert representation above.
The [synthetic clipping example](../examples/v0.3/unsupported-clipping.analyze.json)
shows a stable unsupported diagnostic without copying an external SVG.

## Productized `tfsb analyze`

### Command and source snapshot

```text
tfsb analyze <directory-or-archive>
  [--json]
  [--details <output.ndjson>]
```

Input type is determined by lstat and ZIP signature, not filename alone. A
directory means its present filesystem bytes; Git metadata is ignored. A Git
operator obtains HEAD semantics by creating an archive outside TFSB. The
directory walker does not follow symlinks, records a sorted entry inventory,
opens regular files without following links, validates identity/size before
and after reading, and rescans directory inventories before accepting output.
Any change produces `ANALYZE_SOURCE_CHANGED`, exit 1, and no authoritative
detail file.

ZIP analysis uses the v0.2 central-directory, portable-name, duplicate,
traversal, CRC, compression, and bounded-read controls with the larger
read-only limits below. The opened archive file is hashed/read through one
snapshot and revalidated before output. No archive entry is extracted into the
source tree.

### Resource contract

| Limit | Value |
| --- | ---: |
| candidate entries | 100,000 |
| SVG files | 50,000 |
| one SVG raw bytes | 8 MiB |
| aggregate SVG raw bytes | 512 MiB |
| raw ZIP file | 512 MiB |
| aggregate declared ZIP bytes | 1 GiB |
| compression ratio | 100:1 |
| XML elements in one SVG | 250,000 |
| XML elements in one analysis | 2,000,000 |
| modeled elements in one asset | 1,024 |
| group nesting depth | 8 levels |
| human/aggregate samples per diagnostic | 20 |

The 128-asset and 32-MiB selected mutation limits do not apply to read-only
analysis. Conversely, passing analysis does not authorize import above those
limits.

### Output and taxonomy

Inventory counts every element, attribute, namespace, presentation field,
paint family, transform function, local/external reference, accessibility
signal, XML node class, resource breach, and identity collision independently.
Classification then evaluates combined features per file.

`commonV03` must not classify canonical output from an accepted schema-1 or
schema-2 model as unsupported or unsafe solely because its classifier repeats
the accepted grammar differently. Closed lexical/value recognizers may be
shared inside the analyzer, but inventory remains independent and continues
through later unsafe content. The real schema-version parser and canonical
writer remain the semantic authorities for import, build, and lifecycle
behavior; the analyzer is an inventory-first compatibility oracle, not a
replacement parser.

`analyze` is an additive `JsonCommand`; `JsonStatus` and `JsonExitCode` remain
unchanged. Its aggregate data names both evaluated profiles so a later profile
requires an analyzer schema revision rather than changing an existing field's
meaning:

```text
AnalyzeJsonData
  scanCompleted = true
  input.kind = directory | archive
  totals = files, svgFiles
  profiles.schema1
    profile = tfsb-svg-schema-1
    counts = directlyImportable, importableWithNormalization(0), unsupported, unsafe
    diagnosticCounts, featureCounts, normalizationCounts(empty)
  profiles.commonV03
    profile = tfsb-svg-common-v0.3
    counts = directlyImportable, importableWithNormalization, unsupported, unsafe
    diagnosticCounts, featureCounts, normalizationCounts
  resourceObservations, identity, samples-by-profile
```

Every SVG has one classification in each profile. Schema 1 has no normalization
category, so its aggregate field is present and always zero. Feature inventory is
profile-independent, describing observed SVG constructs; both `schema1` and `commonV03`
report `featureCounts` from the common inventory pass. Command status/exit uses only
`commonV03`. Human output names both profile identifiers. Top-level envelope diagnostics
are at most 20 deterministic representative `MachineDiagnostic` records per public code,
deduplicated by `(code, domain, location, message)` across profiles; complete per-code
counts live in the applicable profile data. Envelope diagnostics strictly follow
`mapMachineDiagnostic` (emitting only `modelLocation` for `domain: "svg"`, `path` for file
operations, and `archiveEntry` for archives). Normalization-required facts live only in typed
`normalizationCounts`/detail normalizations, never as warning/info diagnostics.

The envelope mapping is closed:

| Result | Status / exit | Data |
| --- | --- | --- |
| complete scan; every target-profile file direct | `ok` / 0 | complete, `scanCompleted: true` |
| complete scan; target profile has normalization-required or unsupported, no unsafe | `drift` / 2 | complete, `scanCompleted: true` |
| complete scan; target profile has any unsafe file | `error` / 1 | complete, `scanCompleted: true` |
| input/archive/scan-wide resource/snapshot/operational failure prevents completion | `error` / 1 | `null` |

Data presence is the envelope discriminant. `scanCompleted: true` additionally
prevents a complete unsafe inventory from being confused with partial data.

`--details` produces closed `tfsb-analyze-details` schema version 1 NDJSON:
one header naming `schema1` and `commonV03`, one deterministic record per SVG,
and one footer. Each file record contains `profiles.schema1` and
`profiles.commonV03`, each with its profile identifier, classification,
diagnostic/feature codes, and typed locations; only `commonV03` contains typed
normalization identifiers. The footer repeats per-profile counts and contains
`recordsSha256`, SHA-256 over the exact UTF-8 bytes of every preceding canonical
JSON line including each LF.

Details output has invocation authority rather than presumed project authority:

1. A relative target resolves beneath the invocation working directory and
   may not escape it. An absolute target is allowed. The existing parent must
   be traversed component-by-component without following symlinks; every
   component must be a real directory.
2. The target must be absent and non-symlink at planning and publication. It
   must be disjoint from the analyzed directory or archive. Analyzing `.` may
   therefore use an explicit absolute sibling target, but not a target inside
   `.`.
3. Project discovery starts from the invocation working directory only. When a
   TFSB project is found, `.tfsb`, configured build/install/companion
   destinations, preview, and protected generated/source trees are rejected.
   With no discovered project, no project policy is invented. Details never
   becomes canonical/generated TFSB state.
4. Capture the validated parent identity and absent-target snapshot. Create one
   unpredictable sibling temp with exclusive no-follow creation and mode 0600,
   stream all bytes, fsync and close it, revalidate the complete input snapshot,
   parent identity, and target absence, then atomically hard-link temp to target.
   The link operation supplies no-overwrite publication; fsync the parent,
   unlink only the owned temp, and fsync the parent again. If same-filesystem
   link publication is unavailable, fail closed rather than falling back to an
   overwriting rename.
5. Before successful publication, any race or failure removes only the exact
   owned temp. After target publication, cleanup failure reports the exact
   owned residue without deleting or overwriting the complete target.

The exact public taxonomy and normalization vocabulary are also published as
[machine-readable contract data](../evaluations/v0.3-analyze-contract.json).
Internal `SVG_*`, `XML_*`, exception, and parser strings never escape as public
codes. Public mapping is closed by result domain:

| Domain | Exact public codes | Complete result |
| --- | --- | --- |
| unsafe | `ANALYZE_UNSAFE_XML_DECLARATION`, `ANALYZE_UNSAFE_ACTIVE_ELEMENT`, `ANALYZE_UNSAFE_ACTIVE_ATTRIBUTE`, `ANALYZE_UNSAFE_EXTERNAL_REFERENCE` | `unsafe`, error/1, complete data |
| unsupported | `ANALYZE_UNSUPPORTED_ELEMENT`, `ANALYZE_UNSUPPORTED_ATTRIBUTE`, `ANALYZE_UNSUPPORTED_CSS_CLASS`, `ANALYZE_UNSUPPORTED_VERSION`, `ANALYZE_UNSUPPORTED_NAMESPACE`, `ANALYZE_UNSUPPORTED_PAINT`, `ANALYZE_UNSUPPORTED_TRANSFORM`, `ANALYZE_UNSUPPORTED_XML_NODE` | `unsupported`, drift/2 |
| invalid | `ANALYZE_INVALID_ROOT`, `ANALYZE_MISSING_ARTWORK`, `ANALYZE_INVALID_VIEWBOX`, `ANALYZE_INVALID_CANVAS_DIMENSION`, `ANALYZE_INVALID_ID`, `ANALYZE_INVALID_GEOMETRY`, `ANALYZE_INVALID_PATH_DATA`, `ANALYZE_INVALID_ACCESSIBILITY`, `ANALYZE_INVALID_REFERENCE`, `ANALYZE_INVALID_SHAPE_RENDERING` | `unsupported`, drift/2 |
| syntax/encoding | `ANALYZE_SYNTAX_ERROR`, `ANALYZE_INVALID_UTF8` | `unsupported`, drift/2 |
| per-file/profile bounds | `ANALYZE_FILE_BYTE_LIMIT_EXCEEDED`, `ANALYZE_FILE_ELEMENT_LIMIT_EXCEEDED`, `ANALYZE_PROFILE_ELEMENT_LIMIT_EXCEEDED`, `ANALYZE_PROFILE_DEPTH_LIMIT_EXCEEDED` | `unsupported`, drift/2 only after the bounded streaming inventory completes |
| scan-wide resource | `ANALYZE_CANDIDATE_LIMIT_EXCEEDED`, `ANALYZE_SVG_FILE_LIMIT_EXCEEDED`, `ANALYZE_AGGREGATE_BYTE_LIMIT_EXCEEDED`, `ANALYZE_ANALYSIS_ELEMENT_LIMIT_EXCEEDED` | error/1, `data: null` |
| archive resource | `ANALYZE_ARCHIVE_BYTE_LIMIT_EXCEEDED`, `ANALYZE_ARCHIVE_DECLARED_BYTE_LIMIT_EXCEEDED`, `ANALYZE_ARCHIVE_COMPRESSION_RATIO_EXCEEDED` | error/1, `data: null` |
| archive/input/snapshot/output | `ANALYZE_ARCHIVE_INVALID`, `ANALYZE_INPUT_INVALID`, `ANALYZE_SOURCE_CHANGED`, `ANALYZE_SNAPSHOT_FAILED`, `ANALYZE_DETAILS_TARGET_INVALID`, `ANALYZE_DETAILS_WRITE_FAILED` | error/1, `data: null` |

If an implementation cannot finish bounded inventory after a per-file/profile
breach, it must return the scan-wide failure form with `data: null`; it may not
publish drift from partial inspection. Unsupported geometry, path, or local
reference remains drift/2 when the full scan completes and no unsafe file
exists. Messages never become machine discriminants and never quote source
values.

## Explicit import normalization

```text
tfsb import icons.zip --normalize exact-common --dry-run
tfsb import icons.zip --normalize exact-common \
  --normalization-map normalization.toml --dry-run
```

`exact-common` authorizes only named exact-semantic mappings:

- title-only to `labelled`, generating deterministic IDs;
- root presentation into the typed document table;
- default SVG namespace/version canonicalization;
- definition-order canonicalization (placing `<defs>` ahead of artwork in canonical serialization);
- local xlink to SVG 2 href;
- omitted SVG numeric defaults to explicit normalized numbers;
- one rect corner radius to the typed equal-radius form; and
- preservation of basic primitives and selected transforms.

It does not choose an unlabeled accessibility mode, convert a named CSS color,
flatten geometry, remove a clip/mask/filter, inline a stylesheet, resolve an
external URL, or change identity. Unsupported and unsafe files fail the entire
selected import before planning canonical state.

A closed map is required for unlabeled input:

```toml
schema_version = 1

[defaults]
unlabelled_mode = "consumer_labelled"

[[entry]]
source = "icons/spinner.svg"
accessibility = "decorative"
```

The optional default is itself explicit per-run authority and every affected
entry remains visible in the plan. Entry rules override it. A map source is an
exact normalized archive entry; globs, regex, and basename-only matching are
absent. Mapping cannot supply collection prefixes or path-derived IDs.

The schema-version-1 normalization identifier vocabulary is closed and sorted
in typed output: `accessibility_authority_required`,
`canonicalize_definition_order`, `canonicalize_svg_version`,
`declare_decorative`, `geometry_defaults_expanded`,
`labelled_ids_and_references`, `promote_root_presentation`,
`rect_corner_completion`, `title_only_to_labelled`, `xlink_href_to_href`, and
`xlink_namespace_to_svg2_href`. Adding or changing an identifier requires an
analyze/details schema revision. The earlier proposed
`ANALYZE_NORMALIZATION_*` diagnostic family is retired before implementation;
normalizations are typed data and never machine diagnostics.

Normalization policy identity is frozen as follows:

- policy ID `exact-common`, policy version `1`, target schema version `2`;
- normalization-map schema version `1`;
- canonical map bytes are UTF-8 TOML with final LF: `schema_version` first,
  optional `[defaults]` second with its closed keys in schema order, then
  `[[entry]]` records sorted by normalized `source` using UTF-8 byte order;
  every entry emits `source` then its closed authority fields in schema order,
  using the canonical TOML string writer and no comments or insignificant
  whitespace;
- `mapSha256` is `sha256:<hex>` over those canonical bytes, or `none` when no
  map exists; and
- the policy digest is SHA-256 over the ASCII basis
  `tfsb-normalization-policy-v1\n`, followed by this exact compact JSON object
  and one LF:

  ```json
  {"policyId":"exact-common","policyVersion":1,"targetSchemaVersion":2,"mapSchemaVersion":1,"mapSha256":"<sha256:hex-or-none>"}
  ```

Provenance stores `policyBasis`, `policyId`, `policyVersion`,
`targetSchemaVersion`, `mapSchemaVersion`, `mapSha256`, `policyDigest`, and the
policy implementation version that produced the plan. It never stores an
absolute or relative map path. Formatting-only changes parse to identical
canonical map bytes and preserve the digest; any semantic authority change
changes canonical bytes and the digest. A behavior-changing implementation
requires a new policy version. A semantics-preserving implementation repair may
retain policy version 1, but reconcile still records the current implementation
version and must reproduce the stored normalized checkpoint.

If the original map is unavailable, existing canonical state remains valid but
reconcile cannot reinterpret changed archive input: it reports explicit policy
authority required and performs no mutation. A separately supplied map is
accepted only when canonicalization reproduces the stored `mapSha256` and
policy digest; textual similarity or a path match is irrelevant.

Dry-run output includes source classification, each exact/intentional
normalization, every rejected feature, derived asset ID, accessibility mode,
and semantic disposition. Apply requires the same plan snapshot and retains
the 128-selected/32-MiB transaction boundary.

Until explicit normalization lands, direct schema-2 import is authorized by a
successful real schema-2 parse plus exact canonical SVG byte equality. Analyzer
normalization classification does not gate that path. Noncanonical input fails
with `IMPORT_NORMALIZATION_REQUIRED`, and an already initialized target remains
guarded by `ROOT_ALREADY_INITIALIZED` before project mutation.

Ordinary import with explicit normalization authority accepts only directly
importable or policy-normalizable input.
Manifest import verifies manifest bytes and IDs first, then applies the same
profile and normalization rules. Reconcile requires the same policy/map to
interpret changed source; it never reuses unstored CLI intent implicitly.
Provenance records the normalized source checkpoint and policy digest. Archive
diff reports both raw-source classification and normalized semantic changes.
Bundle serializes canonical semantics only; round trips do not recreate the
original noncanonical XML.

## Migration, digests, and provenance

```text
tfsb migrate --check [--json]
tfsb migrate [--json]
```

Migration is project-wide because projects cannot mix schemas. `--check` is
read-only and produces the exact plan. Apply parses the complete schema-1 tree,
maps each asset to schema-2 `labelled`, preserves title, description, IDs,
focusability, metadata, definitions, paths, groups, uses, transforms,
presentation, asset IDs, filenames, project policy, and companions, then
requires byte-equal fresh SVG serialization for every asset.

The equivalence obligation covers every shared schema-1 shape, not one example:
all root attribute combinations; shared path/group presentation and transforms;
the schema-1 use order `id`, `href`, `x`, `y`, presentation, `transform`;
gradient/stop order; and definition category plus within-kind array order. The
[synthetic schema-1 source](../examples/v0.3/schema-1-ordering-source.svg) and
[canonical golden](../examples/v0.3/schema-1-ordering-golden.svg) freeze the
current writer for TFSB32. TFSB32 must run the same models through the schema-2
writer and compare exact fresh bytes before TFSB33 may migrate them.

Migration JSON uses the existing CLI envelope independently of project schema.
Its closed data shape is:

```json
{
  "mode": "check",
  "fromSchemaVersion": 1,
  "toSchemaVersion": 2,
  "assetCount": 10,
  "companionCount": 1,
  "svgEquivalentCount": 10,
  "files": [
    {
      "path": ".tfsb/assets/favicon-on-dark.toml",
      "beforeBasis": "tfsb-asset-toml-v1",
      "beforeDigest": "sha256:<digest>",
      "afterBasis": "tfsb-asset-toml-v2",
      "afterDigest": "sha256:<digest>",
      "svgOutputDigest": "sha256:<digest>",
      "svgEquivalent": true
    }
  ],
  "provenanceTransition": "schema_migration_checkpoint",
  "applied": false
}
```

Records are complete, sorted by project-relative path, and contain no raw TOML
or SVG. `mode` is `check` or `apply`; `applied` becomes true only after the
complete transaction is active. The envelope is `drift`/exit 2 for an
available check, `ok`/exit 0 for an already-v2 check or successful apply, and
`error`/exit 1 for any invalid, unsafe, or failed migration.

Schema-1 comments/formatting are intentionally replaced by canonical schema-2
TOML. Companion bytes remain exact. Existing build/install/preview outputs are
untouched. Build receipts become source-stale because TOML bytes changed; a
later explicit build refreshes them. Migration never installs.

Digest bases are:

- frozen `tfsb-asset-toml-v1` for schema-1 canonical TOML;
- frozen `tfsb-asset-toml-v2` for schema-2 canonical TOML; and
- `tfsb-svg-output-v1` for canonical SVG byte equivalence across versions.

Provenance schema 2 separates optional archive evidence from mandatory
migration-transition evidence. Each migrated asset can carry this closed shape:

```text
archive = null | {
  sourceBasis, sourceDigest,
  canonicalBasis = tfsb-asset-toml-v1,
  canonicalDigest
}
migration = {
  beforeBasis = tfsb-asset-toml-v1,
  beforeDigest,
  afterBasis = tfsb-asset-toml-v2,
  afterDigest,
  svgBasis = tfsb-svg-output-v1,
  beforeSvgDigest,
  afterSvgDigest,
  svgEquivalent = true,
  resolution = schema_migration_accepted_divergence
}
normalizationPolicy = null | { policy identity fields defined above }
```

`archive: null` means no archive evidence exists; it never means the current
canonical digest was observed in an archive. Migration behavior is closed for
all starting states:

1. With no provenance, migration succeeds and creates only the truthful
   canonical/SVG `migration` transition; `archive` remains null. It invents no
   archive checkpoint.
2. With valid partial provenance, every existing tracked archive checkpoint is
   preserved exactly. Untracked assets retain `archive: null` and gain only
   their canonical/SVG migration transition.
3. With complete provenance, every v1 archive/canonical relation is preserved
   exactly and each asset gains the independent migration transition.

An older unchanged archive can still match a preserved v1 checkpoint while the
migrated canonical state remains accepted divergence. An asset with
`archive: null` has no old-archive convergence claim; a supplied archive is
fresh input and enters ordinary validation/conflict handling. A changed archive
is normalized under explicit policy identity and enters the existing paired-
checkpoint conflict model. No checkpoint bypasses fresh validation, and no
migration record changes diff/reconcile from unknown archive history to known
history.

Diff maps schema-1 accessibility to equivalent schema-2 `labelled` semantics.
An equivalent migration has no artwork diff; provenance reports schema and
digest-basis transition separately. New modes, presentation, geometry, and
transforms use typed semantic locations. Primitives are not compared as
flattened path data.

Migration uses the existing lock/stage/reparse/revalidate/backup/promote/
rollback transaction. Any parse, output-equivalence, snapshot, stage, or
promotion failure preserves the complete old schema or reports exact recovery
residue. There is no automatic down-migration.

## Compatibility evidence and acceptance targets

The deterministic non-product projection remains historical provisional
evidence. It recorded the intended staged profile while deliberately omitting
complete path, value, ID, placement, reference, cycle, and profile-bound
validation. TFSB31R1 reconciled that projection against two independent runs of
the committed product analyzer over exact tracked regular-SVG blobs. TFSB32R1
then corrected the analyzer's omission of canonical local-gradient fallback
grammar and remeasured the same pins; the corrected outputs and counts are
byte-identical because no pinned blob uses that exact syntax. The
[authoritative analyzer dogfood baseline](../evaluations/v0.3-analyzer-dogfood-baseline.md)
records both profiles, manifest digests, source-safety results, complete
aggregate evidence, and every delta. The original
[projection report](../evaluations/v0.3-compatibility-projection.md) and JSON
remain truthful historical evidence rather than being rewritten.

These corrected common-v0.3 counts are the compatibility thresholds consumed
by TFSB33 through TFSB35:

| Corpus | Direct | Normalizable | Unsupported | Unsafe | ID-collision affected |
| --- | ---: | ---: | ---: | ---: | ---: |
| Lucide | 0 | 2,147 | 89 | 20 | 33 |
| Simple Icons | 0 | 3,453 | 0 | 0 | 0 |
| Tabler Icons | 0 | 6,184 | 1 | 225 | 2,109 |
| theSVG | 2 | 8,022 | 3,644 | 789 | 12,444 |

Directly importable remains a strict no-normalization-authority category.
Normalizable means the product found only typed transformations requiring the
declared authority; it is not lifecycle readiness. Identity, legal and
redistribution review, resource and mutation limits, normalization authority,
and source-tree safety remain independent.

Repository source safety and SVG profile measurement are separate. Lucide,
Tabler Icons, and theSVG full tracked exports complete analysis and have the
same profile counts as their regular-SVG corpora. The Simple Icons tracked
export contains `.nvmrc` at Git mode `120000`; directory analysis correctly
fails closed with `ANALYZE_SNAPSHOT_FAILED` and no authoritative partial data.
Its profile counts therefore come from an evidence-only corpus of exact tracked
regular SVG blobs. This does not make the original tree an accepted analyzer
input and does not authorize an ignore-symlinks mode.

v0.3 acceptance requires:

1. product `analyze` produces authoritative, deterministic per-profile counts
   for the pinned regular-SVG tracked-blob corpora using the corrected closed
   TFSB32R1 contract, while full-export source safety is reported independently;
2. every provisional discrepancy is reconciled by exact rule and tracked-blob
   representative in the reviewed authoritative baseline. The historical
   projection JSON remains byte-preserved because its `authority` block already
   declares provisional counts and names the product producer; the linked
   projection report supplies its reviewed follow-up rather than pretending the
   historical machine result was always authoritative;
3. title-only, unlabeled presentation-heavy, individual outline/filled, and
   combined unsupported/unsafe corpus families remain explicitly explainable
   by typed profile results rather than element prevalence;
4. unsafe findings never become normalizable within one product result; a
   corrected provisional unsafe classification may move only through an
   explicit classifier-delta disposition;
5. theSVG remains rejection and backlog evidence: no full-tree import target,
   and all 12,444 collision-affected files remain independently blocked from a
   whole-tree lifecycle claim;
6. no file over 8 MiB is imported; the measured corpora currently have zero;
7. legally reviewed, collision-free local-only 16/32/128 shards complete the
   v0.3 lifecycle without raising mutation limits; and
8. Terminal Nova schema migration produces exact SVG bytes and clean semantic
   diff while truthfully transitioning provenance.

The authoritative counts are tied to the exact revisions and manifest digests
recorded in the baseline. A different corpus revision is a new measurement,
not a reason to force old counts through a hash gate.

## Dogfood, fixtures, visual, and legal strategy

| Corpus | Local-only shard plan | Role |
| --- | --- | --- |
| Simple Icons | deterministic relative-path 16 and 32; optional 128 after per-icon review | title-only accessibility and flat identity |
| Lucide | deterministic 16, 32, and 128 from `icons/` | root stroke/currentColor, shapes, mixed features |
| Tabler | separate deterministic outline and filled 16/32; paired collision-free 128 | presentation, primitive/path mix, variant comparison |
| theSVG | no import acceptance shard in v0.3; optional rejection inventory set only | unsafe/unsupported and identity evidence |

Shard manifests record corpus origin, pinned revision, exact relative paths,
source hashes, selection rationale, and legal disposition. They are local-only
and tests skip with a clear reason when the matching checkout/export is absent.
Tests read tracked blobs, never working-tree bytes. No dogfood file is a direct
fixture source in TFSB30.

Synthetic fixtures are preferred for security rejection, combined features,
edge values, nesting, cycles, and normalization failures. A small external SVG
may enter the repository only after separate exact-asset provenance, license,
attribution, trademark, and redistribution review. Repository-level licensing
alone is insufficient.

Visual qualification compares source and canonical output at the source
viewBox plus 16, 24, 32, 64, 128, and 256 CSS pixels where meaningful. Exact
pixel comparison in Chromium covers every shard; Firefox and WebKit cover each
accessibility/presentation/geometry/transform family and representative
outline/filled cases. Schema-1 migration requires byte equivalence before
browser evidence. Rendering success does not weaken security rejection.

## Dispatcher sequence and implementation boundary

1. **TFSB30 — architecture and compatibility projection.** Close the profile,
   analyzer, accessibility, normalization, migration/provenance, acceptance,
   examples, and v0.3/v0.4 boundary. No product command is implemented.
2. **TFSB31 — productized analyze.** Implement directory/ZIP snapshot
   inventory, explicit schema-1/common-v0.3 profile classifications, stable aggregate JSON, bounded human
   samples, optional atomic NDJSON details, limits, and complete corpus
   qualification. Do not add schema 2 or mutation. The exact assignment is
   [TFSB31](../implementation/tfsb31-dispatcher-assignment.md). TFSB31R1
   reconciles the resulting authoritative baseline and source-safety semantics
   before schema-2 work.
3. **TFSB32 — schema-2 core.** Add version dispatch, accessibility modes,
   presentation, currentColor, six primitives, mixed bounded groups, selected
   transforms/references, TOML/SVG writers, diff/preview support, and frozen
   schema-1 regressions. Do not add migration/import normalization. The exact
   assignment is [TFSB32](../implementation/tfsb32-dispatcher-assignment.md).
   TFSB32R1 restores canonical analyzer/profile parity and refreshes the
   authoritative baseline without changing schema semantics.
4. **TFSB33 — migration and explicit normalization.** Add provenance schema 2,
   digest bases, migrate check/apply transaction, exact-common policy, closed
   mapping, dry-run ledger, and import/reconcile/diff/bundle interaction. The
   exact assignment is
   [TFSB33](../implementation/tfsb33-dispatcher-assignment.md).
5. **TFSB34 — dogfood shards and cross-feature hardening.** Qualify legally
   reviewed local-only 16/32/128 shards, browser evidence, resource/security
   limits, combined features, and acceptance counts. Do not raise lifecycle
   limits or add collection identity.
6. **TFSB35 — Gemini release candidate.** Only after dispatcher issues are
   retired, perform bounded compatibility polish, public docs, packaging,
   versioning, and release qualification. No architecture redesign.
7. **TFSB36A/B — Gemini publication.** Create the public release candidate and
   separately publish/tag/release under explicit publication authority.

Dispatcher phases retain ownership until schema versioning, accessibility and
normalization authority, migration/provenance, unsafe XML, and dogfood
thresholds have executable closure. Gemini begins only after those decisions
are implementation facts. Material failure returns to dispatcher architecture
or correction rather than being polished around.

## TFSB30 verification boundary

TFSB30 verifies the non-product projection helper, deterministic projection
JSON, generic TOML syntax, internal migrated SVG equality, documentation links,

It does not claim that `tfsb analyze`, schema 2, normalization, or migration is
implemented. Product behavior requires TFSB31–TFSB34 executable evidence.
