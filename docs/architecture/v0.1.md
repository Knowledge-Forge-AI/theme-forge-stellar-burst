# Theme Forge Stellar Burst v0.1 Architecture

Status: proposed for the first implementation phase  
Decision record: [ADR 0001](../decisions/0001-declarative-svg-language.md)  
Concrete syntax: [v0.1 examples](../examples/v0.1/README.md)

## Purpose

Theme Forge Stellar Burst (TFSB) is a small TypeScript/Node CLI for treating a bounded class of SVG artwork as project configuration:

```text
selected SVG archive entries
  -> tfsb import
  -> .tfsb/project.toml and .tfsb/assets/*.toml
  -> tfsb build
  -> canonical generated SVG files
  -> tfsb install
  -> configured in-project consumer files
  -> tfsb check
  -> canonical-source, build, and installation status
```

After import, `.tfsb` is the only artwork authority. The input archive is provenance, not a second source of truth. TFSB owns validation, normalization, deterministic serialization, build/install planning, and drift reporting. It does not own logo design, SVG optimization, arbitrary transformations, remote retrieval, or a general XML model.

## Architectural boundaries

### Functional core and imperative shell

The implementation should consist of small functions around immutable values:

```text
bytes -> parse -> validate -> normalized model -> serialize -> bytes
paths + model -> plan -> validated operations -> filesystem commit
```

The functional core owns TOML/XML decoding, validation, normalization, reference checks, canonical SVG serialization, hashing, and plans. A thin Node shell owns root discovery, bounded file reads, staging, atomic replacement, and CLI presentation. No database, plugin system, class hierarchy, network client, watch mode, or general installer is required.

Likely modules are `root`, `toml`, `svg`, `archive`, `build`, `install`, `check`, and `cli`. These are responsibility boundaries, not a commitment to one file per name.

### Authority and generated state

- `.tfsb/project.toml` and `.tfsb/assets/*.toml` are canonical source.
- The configured build directory is entirely generated and replaceable.
- Installation destinations are generated copies, never alternate artwork sources.
- A build receipt records its receipt kind/schema, the configured project-relative `build.directory`, source hashes, output hashes, and tool version. It never records the absolute project root. The marker proves only that the configured generated directory is TFSB-owned; it never bypasses current parsing, validation, or fresh output computation.
- The original archive and imported SVG files are not consulted by `build`, `install`, or `check` after import.

## Project layout

```text
<project-root>/
  .tfsb/
    project.toml
    assets/
      favicon.toml
      mark.toml
      lockup-horizontal.toml
  brand/
    dist/                         # generated; ignored by the current dist/ rule
      favicon.svg
      theme-forge-terminal-nova-mark.svg
      theme-forge-terminal-nova-horizontal.svg
      .tfsb-build.json            # optional generated diagnostic receipt
  docs/
    public/favicon.svg            # installed copy
    src/assets/brand/*.svg        # installed copies
```

Every TOML file has integer `schema_version = 1`. The CLI's product version may be `0.1`; schema and product versions are deliberately independent. Unknown versions fail before field decoding. Schema 1 is closed: adding, removing, or changing a field requires a new schema version, while serializer/parser bug fixes do not. Schema migration is deferred and is not a v0.1 CLI command.

The current repository `.gitignore` pattern `dist/` also ignores `brand/dist/`. v0.1 therefore treats canonical builds as reproducible, untracked artifacts. Committing builds would require a later, explicit repository-policy decision and a narrow ignore exception.

## Root and path contract

For `build`, `install`, `check`, and `list`, the project root is the nearest ancestor containing `.tfsb/project.toml`. `--root <directory>` starts discovery at that directory and still requires the marker there. Import into an uninitialized project requires `--root`; v0.1 import refuses an existing `.tfsb` so that initialization can have a true directory-level commit.

The explicitly named input archive may be outside the project root and is read-only. Every configured path, staging path, generated output, receipt, and install destination must be inside the real project root.

Configured paths use `/` separators and must be relative. Validation rejects absolute paths, drive or UNC prefixes, backslashes, NULs, empty segments, `.` or `..` segments, and duplicate normalized targets. Resolution uses the real project root; existing path components are inspected without following symlinks, symlink components and symlink targets are rejected, and confinement is rechecked immediately before replacement. Lexical `startsWith` checks alone are insufficient.

### Path disjointness and ownership invariants

To prevent accidental data loss and circular drift:
1. **Mutual disjointness:** `.tfsb`, the configured `build.directory`, and every configured install destination must be mutually disjoint. No install destination may reside within `.tfsb` or `build.directory`, and `build.directory` cannot reside inside `.tfsb` or an install directory.
2. **Build directory protection:** `build.directory` cannot be `.` (project root), cannot start with `.tfsb`, and must not overlap with or encompass protected repository trees (such as `.git`, `.tfsb`, `docs`, `test`, `src`, or `node_modules`).
3. **Build directory ownership:** The build directory is TFSB-owned and wholesale-swapped during build. A valid `tfsb-build-v2` receipt must record the same project-relative `build.directory` as current canonical configuration. This ownership identity survives moving the whole project, while a receipt copied to a differently configured build path does not authorize replacement. Validation rejects configuring `build.directory` over existing non-TFSB source directories.

## Command contracts

### `tfsb import <archive>`

Import inspects the ZIP central directory but never extracts it. With no selectors, all regular `.svg` entries are selected; repeated `--select <entry>` options may select an explicit subset. Selection is exact after archive-name normalization.

Import performs these phases:

1. Resolve the explicit project root and prove `.tfsb` does not exist.
2. Inspect every archive entry name and type. Reject the whole archive for an absolute or traversal name, a backslash, duplicate portable normalized name, symlink or other non-regular file entry, encrypted entry, or resource-limit violation. Directories are allowed but never extracted. A portable name key uses Unicode NFC, `/` segments, and ASCII case-folding after rejecting empty, `.`, and `..` segments. v0.1 fixed limits are 1,024 total entries, 128 selected SVGs, 8 MiB uncompressed per selected SVG, 32 MiB selected aggregate, and a 100:1 per-entry uncompressed/compressed ratio. The implementation also caps the central-directory read at 64 MiB and rejects ZIP64 rather than allowing archive metadata to create an unbounded allocation.
3. Select SVG entries; metadata files such as `.DS_Store` and `__MACOSX` entries are never read as assets.
4. Read only selected entry bodies under fixed per-entry and aggregate size limits.
5. Decode UTF-8 XML, reject unsupported or active content, normalize every selected SVG to the typed model, validate cross-references, assign stable asset IDs/filenames, and render the complete next TOML state in memory. Asset ID derivation takes the entry's base filename stem, applies Unicode NFC, maps ASCII spaces and underscores to `-`, and lowercases ASCII letters. The result must already satisfy the schema-1 lowercase kebab-case grammar; non-ASCII or other punctuation fails instead of being silently discarded. The generated filename is `<asset-id>.svg` (for example, `theme-forge-terminal-nova-mark.svg` remains `theme-forge-terminal-nova-mark.svg`). If two entries derive the same asset ID or filename (e.g. `light/mark.svg` and `dark/mark.svg`), import fails closed with an `ARCHIVE_COLLISION` diagnostic naming both entries. The concise checked-in examples are curated, human-edited schema examples rather than literal import output; users may rename imported IDs and update references declaratively.
6. Write the complete `.tfsb` tree to a same-parent temporary directory, fsync files as supported, and rename the directory to `.tfsb` only after all writes succeed.

Any inspection, parse, schema, collision, reference, or serialization error occurs before the canonical tree is written. A failed validation leaves no `.tfsb`; cleanup failure may leave only a clearly non-canonical temporary directory. Re-import/merge and overwrite behavior are intentionally deferred rather than weakening the v0.1 transaction.

### `tfsb build [--dry-run]`

Build parses and validates the complete canonical project before changing output. It serializes every configured asset in memory, rejects filename collisions, and creates a build plan. `--dry-run` prints the plan and writes nothing.

The build directory is TFSB-owned. Execution writes a complete sibling staging directory and swaps it into place. On platforms where replacing a populated directory cannot be a single rename, the shell uses a backup-and-restore sequence and reports a distinct rollback failure if restoration fails. It never merges around unknown files. The receipt contains receipt kind/schema, project-relative build directory, canonical source hashes, output hashes, and tool version; it is recalculated, not trusted, by later commands. The unreleased absolute-root `tfsb-build-v1` format is intentionally incompatible with v2 and has no migration machinery.

### `tfsb install [--dry-run]`

Install does not trust an earlier validation report. It reparses canonical state, serializes expected SVG bytes, and requires each current build file to match those bytes before planning any copy. It validates all destinations and collisions first. Each copy is staged beside its destination and atomically renamed; an execution failure triggers best-effort rollback from same-directory backups and is reported as either `INSTALL_FAILED_ROLLED_BACK` or `INSTALL_FAILED_PARTIAL`. A backup-cleanup failure after all successful replacements does not roll back installed files and is reported as `INSTALL_BACKUP_CLEANUP_FAILED`.

One asset may have zero destinations or one install rule with multiple destinations. Two assets may not target the same normalized destination. `--dry-run` is read-only.

### `tfsb check`

Check is always read-only and reports independent layers:

| Layer | Meaning | Evidence |
| --- | --- | --- |
| Canonical source validity | TOML parses, schema is supported, paths and references validate. | Current `.tfsb` only. |
| Canonical source drift/change | Source hashes differ from the last generated receipt, or no receipt exists. This is informational, not an error by itself. | Current `.tfsb` versus generated receipt. |
| Build drift | A missing, extra, or byte-different generated SVG differs from a fresh in-memory canonical serialization. | Current `.tfsb` versus build directory. |
| Installation drift | A destination is missing or differs byte-for-byte from its expected canonical build. | Expected build bytes versus every destination. |
| Visual equivalence (CI/test only) | Browser pixels differ from an approved fixture/baseline. Evaluated in development/CI test suites via Playwright; not evaluated by CLI `check`. | Pinned Playwright test harness versus fixture renders. |

Invalid canonical source is reported as invalidity, not mislabeled as drift. A source change is ordinary editing until a workflow requires a clean build. v0.1 `check` does not launch browsers and has no Playwright runtime dependency.

An absent build directory is build drift, not an unbuilt-clean state. An existing build directory without a valid project-owned receipt is unsafe state and exits `1`, because `check` cannot safely interpret arbitrary content as TFSB output.

### `tfsb list`

List is read-only. It reports asset ID, generated filename, build-relative path, and zero or more install destinations after full project validation.

## Error and exit-code model

Core functions return discriminated results; expected user errors do not depend on thrown exception text. A diagnostic contains a stable code, operation, source location where available, TOML key or XML element path, and a human explanation. The CLI may group multiple validation diagnostics but must not continue into mutation.

Only expected parser and schema failures cross that result boundary. Unexpected programmer/invariant failures propagate to the CLI's sanitized `INTERNAL_ERROR` handling and are not relabeled as ordinary XML or TOML syntax errors.

### Process exit codes

- `0`: Success / clean (valid configuration, successful operation, or zero drift on `check`).
- `1`: Operational or validation failure (invalid source syntax, schema violation, archive rejection, path confinement violation, or failed staging/rollback).
- `2`: Drift detected (reported exclusively by `tfsb check` when source, build, or installation drift is present in an otherwise valid project).

Representative diagnostic families are:

- `ROOT_*` for discovery, containment, overlap, and confinement;
- `ARCHIVE_*` for entry names, types, collisions, encryption, and limits;
- `XML_*` for unsafe XML and unsupported SVG syntax;
- `SCHEMA_*` for TOML shape/version failures;
- `REFERENCE_*` for duplicate or unresolved IDs;
- `BUILD_*`, `INSTALL_*`, and `ROLLBACK_*` for plan/commit failures.

Unknown TOML keys, XML elements, attributes, namespace content, paint forms, or transform operations fail closed. Unsupported content is never dropped, approximated, executed, fetched, or written elsewhere.

## Import/build equivalence

Round-trip compatibility is semantic and canonical, not byte preservation.

1. **Normalized structural equality:** TypeScript tests import the original SVG and parse the rebuilt SVG into the same normalized domain model, then deep-compare it. This covers element order, IDs and local references, path data semantics, presentation attributes, gradients/stops, accessibility, normalized metadata text, and parsed transforms.
2. **Canonical SVG bytes:** Serializing the same validated TOML value always yields identical UTF-8/LF bytes. Rebuilding without source changes is byte-identical.
3. **Installed bytes:** Each installed copy must be exactly the expected canonical SVG bytes. No destination-specific rewriting is permitted.
4. **Browser rendering:** A pinned Playwright/Chromium development test renders the original fixture and rebuilt output with fixed viewport, device scale, transparent background, and disabled environmental variation. The hard equivalence gate is zero differing pixels. Firefox and WebKit initially provide load/render/non-empty smoke coverage, not cross-engine pixel identity.

Structural equality deliberately ignores XML declaration presence, indentation, inter-element whitespace, attribute order, quote style, redundant namespace declarations, self-closing syntax, comments, and equivalent decimal spellings. It does not ignore metadata text, child order, paint fallback, IDs/references, geometry, accessibility text, or transform order.

## Canonical SVG serialization

Output is XML 1.0, UTF-8, LF-terminated, with one canonical SVG namespace declaration. A leading UTF-8 BOM is accepted before either the root or optional XML declaration and is not emitted. Element order is title, description, metadata, definitions, then artwork. Definitions use the non-semantic canonical category order linear gradients, groups, then paths, while order within each category is preserved. Attributes use a fixed per-element order, double quotes, XML escaping, and self-closing empty elements. Optional attributes matching standard SVG defaults—including `shape-rendering="auto"`, `gradientUnits="objectBoundingBox"`, and `x="0"` / `y="0"` on `<use>`—normalize to absent domain fields and are canonically omitted. Hex colors canonicalize to uppercase `#RRGGBB`. Comments and redundant namespace declarations are not emitted.

Numeric fields are finite decimal values. Canonical output normalizes negative zero to `0`, adds a leading zero to fractions, removes insignificant trailing fractional zeros, and never emits a plus sign or exponent (`.8`, `0.80`, and `8e-1` become `0.8`; `2.0` becomes `2`). Path `d` remains SVG path syntax: import validates its bounded grammar, converts XML whitespace runs to single spaces, trims it, and otherwise preserves command letters and numeric token spelling. TFSB does not expose a path-command data language.

Transforms are parsed and stored internally as ordered operations. v0.1 accepts only `translate(x)`, `translate(x y)`, `scale(s)`, and `scale(x y)` with finite numbers. Output uses canonical decimals, one space between arguments, and one space between operations. `matrix`, rotate, skew, comma-separated forms, and transform functions on unsupported elements fail explicitly.

## Validation invariants

- Asset IDs and generated filenames are unique within the project.
- Every SVG ID is unique within its asset.
- `href` is exactly a local `#id` and resolves to a supported definition.
- `url(#id)` paint references are local and resolve to a linear gradient.
- Fallback color is allowed only with a gradient paint; import accepts SVG's `url(#id) #RRGGBB` form for `fill` and `stroke`, and TOML stores them as `fill` + `fill_fallback` and `stroke` + `stroke_fallback`. Serialization recombines them with one space (`fill="url(#id) #RRGGBB"` / `stroke="url(#id) #RRGGBB"`).
- Accessibility title and description IDs are unique and `aria-labelledby` is derived in title/description order; root role is always `img`.
- Text-only metadata is supported. XML and TOML accessibility/metadata text use the same line-ending, blank-edge, and common-indent normalization. Nested markup or attributes on `<metadata>` are unsupported.
- Root dimensions are positive unitless numbers; `viewBox` has four finite numbers with positive width and height.
- All arrays preserve declared order. TOML table and key order are not semantic.

## Test strategy

| Suite | Contract proved |
| --- | --- |
| Unit: TOML/model | Schema 1 decoding, unknown-key rejection, closed unions, numeric/paint/transform validation, reference errors, diagnostic locality. |
| Unit: SVG | Safe XML profile, metadata normalization, comments ignored, canonical escaping/order/numbers, path preservation, unsupported-element/attribute rejection. |
| Archive safety | Absolute/traversal/backslash names, normalized duplicates, symlink and non-regular entries, encryption and resource limits; assert no `.tfsb` creation. |
| Fixture round trip | All six Terminal Nova fixtures import; normalized original and rebuilt domain models compare equal. |
| Deterministic build | Repeated and differently ordered TOML inputs serialize to the same expected bytes; missing/extra output is detected. |
| Transaction integration | Import validation failure writes no canonical state; build staging failure restores prior build; install plans all destinations before writing and reports rollback outcome. |
| Install/check | One favicon installs to multiple destinations; exact-byte modifications produce build/install drift independently; invalid source is distinct from drift. |
| Bounded Playwright | The real six-asset import/build/install pipeline feeds exact same-run original/rebuilt/installed screenshot comparisons. Linux Chromium enforces committed zero-tolerance goldens across the role-aware matrix; Firefox/WebKit provide representative render smoke. Playwright remains a development dependency. |

The fast Node/Vitest suite and bounded Playwright suite remain separate: ordinary `npm test` does not download or launch browsers. The documentation examples should be syntax-checked when a TOML parser is available and mechanically cross-checked against the real fixtures for the fields they claim to represent.

## Lessons retained from Terminal Nova

The reference prototype demonstrates useful seams: a generated brand directory, a fixed asset inventory, multiple install targets for one favicon, pre-install validation, path-only lettering, and browser inspection. TFSB moves inventory and destinations into configuration and retains validation-before-mutation.

The prototype's product-specific geometry generation remains product-specific. Its Markdown validation status is not an authority token, its archive writer is not an import safety model, and its destructive prepare/clear sequence is not copied. TFSB always validates current canonical state and expected bytes.

## Intentional exclusions

v0.1 excludes scripts, event attributes, external URLs/resources, images and data URLs, `foreignObject`, HTML, animation, filters, masks, clipping, patterns, markers, symbols, text/fonts, external or inline CSS, raster data, arbitrary namespaces, DOCTYPE/entities, general XML preservation, optimization, templating, remote download, database state, plugins, watch mode, and unrelated asset formats.

## Subsequent implementation roadmap

1. **TFSB1 — language core and fixture proof:** package/test scaffold, reviewed TOML/XML dependencies, schema decoding, normalized SVG import, deterministic serialization, stable diagnostics, and all-six-fixture semantic tests. No filesystem mutation or CLI.
2. **TFSB2 — project and transaction engine:** root/path confinement, safe ZIP inspection, initialization-only import, build/install plans and staging, hashes/receipt, read-only check/list, and the small CLI surface. No browser dependency or remote input.
3. **TFSB3 — bounded visual and end-to-end qualification:** pinned Playwright development setup, Chromium zero-pixel fixture comparisons, Firefox/WebKit smoke rendering, and command-level transaction/drift scenarios. No framework expansion or release work.

Each phase must retain the closed schema and fail-closed behavior. A need for broader SVG syntax, re-import/merge, a new dependency class, or a raw escape hatch returns to design rather than being absorbed opportunistically.

## First implementation recommendation

The next phase should implement only the language core and fixture proof:

- establish the TypeScript package and project-owned unit-test setup;
- choose minimal TOML and safe XML parsing dependencies through the repository's dependency review, without ZIP or Playwright yet;
- implement schema-1 TOML decoding, typed validation, normalized SVG import, and deterministic SVG serialization;
- cover the six existing SVG fixtures plus focused unsupported-content cases;
- expose library functions only, with no CLI, filesystem mutation, archive handling, install engine, visual harness, publication, or migration command.

Acceptance for that phase is: all six fixtures normalize and round-trip structurally; favicon, mark, and horizontal lockup match the checked-in TOML examples; metadata text and paint fallback survive; comments disappear without changing equality; translate/scale and numeric spellings canonicalize deterministically; unsupported syntax produces stable diagnostics; and two serializations of the same model are byte-identical.
