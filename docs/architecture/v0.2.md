## Purpose and release boundary

TFSB v0.2 adds lifecycle operations around the existing schema-1 declarative
SVG language:

- safe inspection and reconciliation of revised local archives;
- deterministic outbound ZIP bundles;
- explicit semantic diff baselines and canonical TOML formatting;
- versioned machine-readable command results; and
- a static, local, browser-runtime-free preview gallery.

The release does not expand the SVG language. Every valid v0.1 project and
asset TOML file remains valid without migration. `schema_version = 1`, the
bounded SVG profile, companion allowlist and byte-integrity contract, Node.js
`>=22`, package name, legal model, and existing `import`, `build`, `install`,
`check`, and `list` human-mode behavior remain in force.

The following remain deferred: schema version 2, broader SVG elements or
attributes, text and fonts, arbitrary filters, general XML escape hatches,
plugins, remote retrieval, watch or daemon mode, databases, interactive merge
editing, and general-purpose file or package installation.

The product command `tfsb analyze`, directory-source analysis, path-derived
asset IDs, strip-prefix/mapping/collection identity, configurable higher
limits, streaming bundle construction, chunked/scripted preview, and NDJSON
are also deferred. The checked `tools/audit-dogfood-corpus.mjs` helper is
architecture evidence, not an installed or exported CLI surface.

## Corpus-scale boundary

The v0.2 lifecycle contract is a bounded project or curated shard, not an icon
warehouse. Import and reconciliation retain the v0.1 archive limits: at most
1,024 ZIP entries, 128 selected SVGs, 8 MiB per selected entry, and 32 MiB
aggregate selected content. The raw archive file is additionally capped at a
fixed 128 MiB. TFSB checks that size before a full scan, validates the ZIP
end-of-central-directory and bounded central directory before computing the
required whole-archive SHA-256 in bounded chunks, and revalidates archive
identity after hashing and selected-entry inspection. A canonical mutation
refuses a complete next tree above 128 assets before staging. Full-corpus
import/reconcile of the measured 2,256- to 12,457-SVG trees is not a v0.2 goal.

The boundary is operation-specific. `list`, `check`, `fmt --check`, and
`diff --provenance` may return complete read-only results for a valid
hand-authored project above 128 assets. Applying `fmt`, default `build`,
`install`, and `preview` reject more than 128 assets before lock or stage
creation. Bundle retains its explicit-subset selection and 128-asset limit;
none of the read-only allowances asserts complete lifecycle support above the
boundary.

Unmanifested imports retain the v0.1 basename-derived identity rule. Exact
selectors may form one collision-free subset from a bounded archive, but they
cannot import two paths that derive the same asset ID. A verified TFSB bundle
manifest may preserve its explicit IDs as already specified. Normalized
path-derived IDs and other collection mapping schemes remain a single deferred
design question; opaque hashes are not acceptable ordinary IDs.

The fixed boundary preserves complete-plan transaction semantics. Parsing is
sequential, but all normalized records, rendered next canonical bytes, and
provenance needed for one decision remain bounded and are validated before one
stage/swap. Processing batches may populate only an unpublished complete stage;
no batch may expose canonical mutation before all later validation succeeds.

## Authority and state model

The authority order is unchanged:

1. Freshly parsed and validated `.tfsb/project.toml` and
   `.tfsb/assets/*.toml` define artwork and project policy.
2. Selected `.tfsb/companions/*` files are canonical opaque bytes.
3. `.tfsb/provenance.json` is bounded reconciliation evidence. It is not
   schema-1 source, cannot make invalid TOML or SVG valid, and cannot authorize
   an overwrite by itself.
4. The build directory, build receipt, install destinations, bundles, and
   preview directories are derived state.
5. An input archive is a read-only candidate. Retaining it is never required.

The build receipt and import provenance have different meanings. A build
receipt proves ownership of one generated directory and records build drift.
Import provenance records the last explicitly accepted relationship between a
canonical file and an archive entry. Neither may substitute for the other.
All canonical project readers snapshot and validate `.tfsb` exhaustively,
rejecting unrecognized top-level entries or unallowlisted files across both
mutation and read-only commands.

One `LoadedProject` observation owns the canonical snapshot used for project,
asset, companion, and provenance semantics. Provenance and archive-identity
mapping never reread live provenance after that snapshot. Expensive read-only
operations re-snapshot before returning; `check`, `list`, all four diff modes,
`bundle --dry-run`, `fmt --check`, and preview fail with
`CANONICAL_CHANGED_DURING_PLAN` and exit `1` rather than return stale or hybrid
human or machine output.

## Command surface

The v0.2 command shapes are intentionally small:

```text
tfsb import <archive> [--root <path>] [--record-provenance] [--manifest]
  [--select <entry> ...] [--companion <entry> ...]

tfsb reconcile <archive> [--root <path>] [--dry-run | --apply]
  [--select <entry> ...] [--companion <entry> ...]
  [--resolve <key>=canonical|archive ...]
  [--rename <old-asset-id>=<entry> ...]
  [--rename-companion <old-file>=<entry> ...]
  [--remove <asset-id> ...] [--remove-companion <file> ...]
  [--json]

tfsb check [--root <path>] [--json]

tfsb list [--root <path>] [--json]

tfsb bundle [--root <path>] --output <project-relative.zip>
  [--asset <asset-id> ...] [--companion <file> ...]
  [--force] [--dry-run] [--json]

tfsb diff [--root <path>]
  [--provenance | --archive <archive> | --build | --install]
  [--json]

tfsb fmt [--root <path>] [--check] [--json]

tfsb preview [--root <path>] [--output <project-relative-directory>]
  [--open] [--json]
```

Two opt-in modifiers extend initialization import without changing its default
v0.1 behavior: `--record-provenance` includes aligned provenance in the initial
absent-to-present transaction, and `--manifest` enables the bundle-manifest
round-trip mode described below. With neither flag, import creates the same
canonical file classes and uses the same selection rules as v0.1.

`--record-provenance` captures an expected-absent canonical snapshot
immediately after root validation. Any `.tfsb` observed then is already
initialized. Transaction revalidation and a final pre-promotion existence
check reject a later `.tfsb`; the initialization transaction never treats a
concurrent valid project as the replaceable expected state. Portable rename
does not supply an atomic no-replace primitive for a directory, so this does
not claim exclusion of an empty directory created after that final check.

`reconcile` without `--apply` is read-only; `--dry-run` is an explicit alias
for that default and cannot be combined with `--apply`. Repeated selectors are
exact after the existing portable archive-name normalization. Resolution keys
are asset IDs or `companion:<canonical-file>`.

The selected shape is one principal reconciliation command because archive
classification, collision checks, provenance comparison, and transaction
planning must see the complete candidate at once. Separate add and replace
commands would either duplicate that planner or risk inconsistent partial
decisions. An interactive editor would add state and ambiguous ownership and
is not included.

## Reconciliation model

### Plan before mutation

Every reconcile execution performs the same read-only planning pipeline:

1. Discover and validate the current project without trusting provenance.
2. Inspect the complete ZIP central directory with the existing entry-type,
   portable-name, encryption, ZIP64, and resource-limit checks.
3. Read only selected SVG and companion entries under the existing bounded
   limits.

Project TOML, asset TOML, companions, and provenance used for classification
are decoded from the exact captured canonical snapshot bytes, not reread from
the live `.tfsb` tree. Destination confinement remains a live root check. The
planner re-snapshots `.tfsb` before returning even a read-only plan and fails
with `CANONICAL_CHANGED_DURING_PLAN` if the tree changed. Applying retains the
post-lock precommit comparison. Public plan records and flags are frozen
inspection DTOs; only private planner-owned immutable state can authorize
execution, so copied, forged, deserialized, or publicly modified plans cannot
execute.
4. Parse selected SVGs into the schema-1 normalized model and validate all
   references.
5. Parse and validate provenance independently. Missing records are permitted;
   malformed, duplicate, impossible, or path-inconsistent records fail closed.
6. Resolve explicit mappings, rename requests, removals, IDs, filenames, and
   companion names; reject every ambiguity or collision.
7. Classify every relevant canonical record and archive entry.
8. Reject a complete next project above 128 assets, then render the bounded
   complete next canonical tree in memory, including unchanged bytes, and
   reparse it.
9. Return a deterministic plan. Only `--apply` may pass the plan to the
   canonical transaction shell.

No classifier writes as it discovers an action. A failure in any entry prevents
all canonical mutation.

### Paired checkpoints, not a hidden source tree

For each tracked asset, provenance records two checkpoints:

- `canonicalState = "present" | "absent"` and, when present,
  `canonicalModelDigest`: the canonical state accepted at the last
  reconciliation decision; and
- `archiveModelDigest`: the candidate archive model accepted at that decision.

It also records `resolution = "aligned" | "canonical"`. `aligned` means both
models were equal after the decision. `canonical` means the operator explicitly
kept a different canonical model or an absent canonical record while accepting
the candidate as the new archive checkpoint. This paired state is necessary:
one digest cannot represent an explicitly accepted human divergence or
tombstone without repeatedly reporting a false conflict or later overwriting
it.

For a tracked asset with candidate state in the archive, define:

```text
canonicalChanged = (current presence != recorded canonical presence) ||
                   (current presence == "present" && current model digest != recorded canonical model digest)
archiveChanged   = candidate presence == "present" &&
                   (candidate model digest != recorded archive model digest)
archiveOmitted   = candidate presence == "absent" && recorded archive presence == "present"
```

The planner applies the following normative classification rules:

| Canonical since decision | Archive since decision | Prior resolution | Classification | Default apply behavior |
| --- | --- | --- | --- | --- |
| unchanged | unchanged (present) | aligned | `UNCHANGED` | no writes |
| unchanged | unchanged (present) | canonical | `UNCHANGED_ACCEPTED_DIVERGENCE` | no writes; preserve canonical |
| unchanged | changed (present) | aligned | `ARCHIVE_CHANGED` | update canonical and record aligned checkpoints |
| unchanged | changed (present) | canonical | `CONFLICT` | no writes without per-record resolution |
| unchanged | omitted (absent, recorded present) | either | `ARCHIVE_OMISSION` | read-only report; retain canonical asset and provenance; never delete without explicit `--remove` |
| changed | unchanged (present) | either | `CANONICAL_EDITED` | preserve canonical; advance provenance only with `--resolve <id>=canonical` |
| changed | changed (present), equal to canonical | either | `CONVERGED` | provenance-only aligned update |
| changed | changed (present), different from canonical | either | `CONFLICT` | no writes without per-record resolution |
| changed | omitted (absent, recorded present) | either | `ARCHIVE_OMISSION_CANONICAL_EDITED` | read-only report; retain human canonical edits; never delete without explicit `--remove` |
| absent, recorded absent | unchanged (present) | canonical | `UNCHANGED_ACCEPTED_ABSENCE` | no writes; preserve the tombstone |
| absent, recorded absent | absent, recorded present | canonical | `CONVERGED_ABSENCE` | provenance-only removal of the now-unneeded tombstone |
| absent, recorded present | present or absent | either | `CANONICAL_MISSING` | preserve the absence; require an explicit direction before provenance changes |

`--resolve <key>=archive` explicitly authorizes the selected archive value to
replace that canonical record and records aligned checkpoints.
`--resolve <key>=canonical` explicitly preserves the current canonical value,
records the candidate as the archive checkpoint, records canonical ownership,
and advances `canonicalModelDigest` to the current model digest. This provides
the uniform, documented exit from `CANONICAL_EDITED`, as well as resolving
`CONFLICT` or accepting human changes on `ARCHIVE_OMISSION_CANONICAL_EDITED`.
For `CANONICAL_MISSING`, the canonical direction accepts removal and
records an absent canonical checkpoint while the candidate remains present;
the archive direction restores the selected asset. A record is dropped only
when both canonical and accepted archive state are absent. There is no global
conflict override and no inferred winner.

### Candidate evaluation scope vs selection filter

By default, `reconcile <archive>` evaluates candidate entries across the entire
archive for every currently tracked asset and tracked companion, matching by
entry name and companion filename. An entry is classified as `ARCHIVE_OMISSION`
only when the candidate archive genuinely contains no matching entry for a
tracked item.

When explicit selection filters (`--select <entry>` or `--companion <entry>`)
are provided, unselected tracked records are un-scoped from reconciliation
(preserved untouched in canonical state and omitted from the active
reconciliation plan, rather than treated as candidate absence). Selection
narrows candidate scope; it never implies a resolution or deletion.

### Bootstrap for v0.1 projects and partial provenance

Existing v0.1 projects have no provenance. Absence is not invalid canonical
state and does not affect existing commands. Reconciliation handles it per
record:

- Canonical and candidate models equal: `UNTRACKED_MATCH`. `--apply` may add an
  aligned provenance record without rewriting TOML.
- Canonical and candidate differ: `UNTRACKED_CONFLICT`. `--apply` writes
  nothing unless that record has an explicit `canonical` or `archive`
  resolution.
- Candidate has no canonical counterpart: `NEW_ASSET`; it may be added by
  `--apply` after all identity checks.
- Canonical has no candidate counterpart: `ARCHIVE_OMISSION`; it is retained.

A partially populated manifest follows the same rules record by record.
`tfsb import --record-provenance` writes aligned records in the same initial
`.tfsb` transaction; import without that opt-in retains v0.1 behavior. Thus the
production Terminal Nova project can adopt v0.2 with a matching archive through
a provenance-only transaction, while a mismatched historical archive cannot
manufacture a baseline silently.

### Adds, replacements, omissions, removals, and renames

- A new selected SVG becomes a new asset only if its derived ID, filename,
  canonical TOML path, and generated output do not collide under the existing
  portable comparison rules.
- A changed tracked entry replaces canonical TOML automatically only in the
  `ARCHIVE_CHANGED` aligned case. Human edits always win by default.
- A selected allowlisted companion is compared byte-for-byte. Companion
  destinations in `project.toml` are retained on replacement.
- Archive absence is reporting evidence, never deletion authority.
  `--remove` and `--remove-companion` are explicit per-record authorities. The
  plan reports removal of matching project policy declarations; it never
  deletes existing build or installed copies. Those remain visible as derived
  drift until an independently authorized build/install or operator cleanup.
- An unannounced archive rename is `NEW_ASSET` plus `ARCHIVE_OMISSION`.
  `--rename <old-id>=<entry>` is the only way to assert asset continuity. It
  updates the asset ID, filename, canonical TOML path, project install asset
  references, and provenance record in one transaction while preserving all
  destinations. `--rename-companion` similarly preserves companion
  destinations.
- A rename whose new ID, filename, path, output, or portable key collides with
  another record is `COLLISION` and cannot be resolved by choosing a winner.
- Multiple candidate entries that could map to one canonical record, or one
  entry mapped to multiple records, are ambiguous and fail before planning.

The archive entry name and source archive digest are evidence only. No
machine-local archive path is stored.

## Provenance representation and digest contract

The selected representation is one deterministic
`.tfsb/provenance.json`. It avoids sidecar proliferation and keeps provenance
out of closed schema-1 TOML. Records are a sorted array rather than an object
whose accidental property order becomes meaningful. The complete example is
[provenance.json](../examples/v0.2/provenance.json).
Serialization uses fixed field order, asset records sorted by `assetId` in
ascending UTF-8 byte order (Unicode code point order) followed by companion
records sorted by `canonicalPath` in ascending UTF-8 byte order, two-space JSON
indentation, UTF-8, and one final LF.

Every asset record contains at least:

- `toolVersion` and provenance `schemaVersion`;
- current asset ID and project-relative canonical TOML path;
- source archive SHA-256, with no retained archive path;
- normalized entry name and raw selected-entry SHA-256;
- `digestBasis = "tfsb-asset-toml-v1"`;
- recorded archive and canonical model SHA-256 values; and
- recorded canonical presence; and
- `resolution`.

Every companion record contains its canonical project-relative path, archive
and entry evidence, recorded archive and canonical byte SHA-256 values, tool
version, and resolution. A raw canonical-file digest is deliberately omitted:
it is neither needed for conflict classification nor stable across semantic
formatting.

`tfsb-asset-toml-v1` is SHA-256 over the UTF-8 bytes returned by the frozen
v1 canonical asset-TOML serializer after current bytes have parsed and
validated to a normalized asset. The digest includes the serializer's final LF.
It is a versioned digest algorithm, not an alias for whichever serializer a
future release happens to prefer. A future implementation must retain this
basis while v1 provenance remains supported or introduce an explicit new
basis. Formatting, comments, raw key order, and equivalent TOML spelling do
not affect it.

Provenance is untrusted input, not an authentication mechanism. The loader
rejects unknown fields, unsupported versions or digest bases, invalid digest
syntax, duplicate records, ID/path disagreement for an existing target,
non-portable entry names, and records outside the canonical allowlist. A
structurally valid record whose canonical target is unexpectedly absent is
stale evidence classified as `CANONICAL_MISSING`, not malformed JSON. A record
whose accepted canonical state is absent is a deliberate tombstone. The planner
recomputes current canonical presence/digests and candidate digests before
classifying.
A valid-looking malicious edit by an actor already able to rewrite repository
files cannot be detected cryptographically; repository review and version
control remain the integrity boundary. Provenance never bypasses canonical or
archive validation.

## Deterministic outbound bundles

### Bundle inputs and contents

`tfsb bundle` reparses and validates current canonical state and serializes SVG
bytes fresh in memory. It does not read SVGs from the build directory or install
destinations and does not require either layer to be clean. Invalid canonical
state stops before output creation.

The default includes every asset and every configured canonical companion.
Repeated `--asset` or `--companion` options select a subset. A bundle contains:

- selected canonical SVG serialization under each validated asset filename;
- selected opaque companion bytes under their validated canonical filenames;
  and
- one required root `tfsb-manifest.json`.

It contains no TOML, provenance, build receipt, install policy, absolute path,
username, host, environment value, or executable file. The manifest is
portable evidence and inventory, not validation authority. It includes a
schema version, generator package/version, optional project name, and a
`files` array sorted in ascending UTF-8 byte order (Unicode code point order)
of portable entry `name`, recording file kind, portable name, asset ID where
applicable, and SHA-256. It has no timestamp and does not hash itself.

`tfsb import bundle.zip --manifest --root <new-root>` is the explicit v0.2
round-trip mode. It verifies the reserved manifest and every listed byte,
applies the existing SVG parser and companion allowlist, and uses the listed
asset IDs only after normal validation and collision checks. Install
destinations and build policy are intentionally not transported. Without
`--manifest`, v0.1 import selection behavior is unchanged.

### Canonical ZIP policy

For unchanged validated canonical state and identical selection, bundle bytes
are identical under this policy:

| ZIP property | Canonical value |
| --- | --- |
| Entry set | manifest plus selected regular files; no explicit directory entries |
| Entry names | NFC, `/`, no leading slash, no empty/`.`/`..` segment, portable-key unique |
| Ordering | ascending entry-name UTF-8 bytes (Unicode code point order) after validation |
| Data | exact fresh SVG serialization or exact companion bytes |
| Compression | stored, method 0; no DEFLATE version dependency |
| Modified time | DOS `1980-01-01 00:00:00` |
| Origin/mode | Unix origin, regular file `0100644`, DOS archive bit set |
| Executability | no execute bits; non-regular entries impossible |
| Encoding flag | deterministic `fflate` behavior: UTF-8 flag exactly when required by a non-ASCII name |
| Data descriptor | absent because sizes and CRC are known before writing |
| Extra fields | none |
| Per-file comments | none |
| Archive comment | none |
| ZIP64/multi-disk | absent and rejected |

The existing pinned `fflate@0.8.3` can express this policy through `zipSync`
with a sorted object, `level: 0`, explicit `os`, `attrs`, empty metadata, and a
fixed local-component `Date(1980, 0, 1, 0, 0, 0, 0)`. The local-component
construction matters because this version reads local date fields. A bounded
TFSB20 spike produced identical bytes under UTC and America/New_York. No new
writer dependency is justified. Golden ZIP-header and repeated-byte tests must
pin this behavior; any `fflate` upgrade must requalify the canonical byte
format.

The output path is project-relative and project-confined. It must not be under
`.tfsb`, the build directory, an install destination, or the preview directory.
The target must be absent unless `--force` is present. `--dry-run` validates and
lists the exact entries, sizes, and digests without creating the archive.
Bundle planning also enforces the importer-compatible limits of at most 1,024
total ZIP entries, at most 128 SVG assets, at most 8 MiB per asset or companion,
and at most 32 MiB aggregate selected content. The manifest uses fixed key
order, two-space JSON indentation, UTF-8, and one final LF; its size is checked
before ZIP allocation.

## Semantic diff

One invocation selects exactly one baseline; combinations are usage errors:

- `tfsb diff` and `tfsb diff --provenance` compare current canonical semantic
  and companion-byte digests with both the recorded canonical checkpoint and
  the last accepted archive checkpoint. They therefore distinguish change
  since the previous decision from an accepted or new divergence relative to
  imported archive state. Missing records are reported as untracked. Because
  provenance intentionally stores no hidden model snapshot, this mode reports
  stable per-record identity and hash changes, not invented field-level
  history.
  Both an accepted canonical divergence and an accepted canonical absence are
  differences relative to the archive checkpoint and therefore exit `2`, even
  though they remain non-conflicting clean reconciliation states.
- `tfsb diff --archive <archive>` compares two complete in-memory models:
  current canonical state and selected candidate archive state. This is the
  typed SVG diff mode and does not require provenance.
- `tfsb diff --build` compares fresh canonical SVG bytes and current project
  source hashes with the build directory and receipt. A v0.2 build writes a
  `tfsb-build-v3` receipt containing a compact normalized project-policy
  snapshot (build directory, asset install destinations, and companion
  destinations), with project-relative paths only. Diff can therefore report
  typed policy additions, removals, and destination changes plus missing,
  extra, and byte-different output. Existing v2 receipts remain valid ownership
  evidence for `check`, `build`, and `install`, but typed policy history is
  reported unavailable until the next build writes v3.
  Receipt inspection lstat-checks one non-symlink regular file, enforces a
  fixed 512-KiB ceiling justified by the 128-asset boundary, reads through one
  opened-file snapshot, and revalidates identity and size. Output entries,
  including the receipt during directory validation, must be non-symlink
  regular files. Public `serializeBuildReceipt` strictly normalizes v2/v3,
  sorts hash maps, policy records, and destinations in UTF-8 byte order, and
  emits fixed-order two-space JSON plus one LF independently of caller object
  insertion order.
- `tfsb diff --install` compares fresh expected bytes with configured asset and
  companion destinations and reports destination policy plus missing and
  byte-different files.

Typed archive diffs use stable asset IDs and element positions/IDs. They report
canvas, accessibility, metadata, gradient, stop, element, presentation,
transform, and path-geometry changes. A path change reports old/new
`tfsb-path-text-v1` SHA-256 values and a bounded normalized-text prefix/suffix;
it never claims to interpret artistic intent or arbitrary geometry.
`tfsb-path-text-v1` is defined as the SHA-256 digest over the UTF-8 bytes of the
normalized SVG path `d` attribute string after token and whitespace
normalization (single-space separated command and coordinate tokens as emitted
by the normalized SVG parser). Ordering is asset ID, change category, model
location, then diagnostic code.

Diff is always read-only. A valid difference exits `2`; invalid input or an
undefined requested baseline exits `1`.

The v3 policy snapshot is derived comparison evidence, never canonical state or
import provenance. It has no timestamp or absolute root, cannot authorize
replacement, and is always compared with a freshly parsed project. A v0.2
reader accepts existing v2 receipts; a v0.2 build emits v3 after it has planned
and validated the complete current build.

## Canonical formatting

`tfsb fmt` owns only `.tfsb/project.toml` and `.tfsb/assets/*.toml`. It parses
and validates the complete project, serializes each normalized value through
the canonical TOML writers, reparses the proposed bytes, and proves normalized
model equality before planning a write. It does not alter companions,
provenance, SVG output, build receipts, or install destinations. TOML comments
and noncanonical layout are non-semantic and are removed by canonical output.

`--check` is read-only and exits `2` if any owned TOML byte would change.
Applying `fmt` commits every changed TOML in one canonical-tree transaction.
Semantic provenance digests do not change. The existing build receipt records
raw canonical file bytes, however, so a byte-changing format run makes
`tfsb check` report `source: changed` and exit `2` until a separately authorized
`tfsb build` refreshes generated state. Formatting never runs build or install.

## Versioned JSON command results

`--json` is a deliberate public API for `check`, `list`, `reconcile`, `diff`,
`bundle`, `fmt`, and `preview`. JSON support for `import`, `build`, and `install` is
deferred so v0.2 does not accidentally expose their internal plan shapes;
`preview --json` is introduced in TFSB24.
Human output remains unchanged at ordinary project sizes when `--json` is absent.

Machine JSON is complete and untruncated for every valid read-only project
result, including a larger hand-authored v0.1 project; several thousand records
may therefore produce a multi-megabyte envelope. Human output uses an
implementation-owned threshold of 50 records and may summarize
record lists only when it states the exact total, exact omitted count, and how
to request selectors or `--json`. A mutation, bundle, or preview that exceeds
its supported cardinality returns a stable aggregate resource diagnostic; it
does not emit an authoritative partial record set.

Every supported command emits exactly one UTF-8 JSON object plus LF:

```json
{
  "schemaVersion": 1,
  "command": "check",
  "status": "ok",
  "exitCode": 0,
  "summary": "Canonical, build, and install state are clean.",
  "diagnostics": [],
  "data": {}
}
```

The envelope fields are closed and intentionally serialized; internal class or
exception objects are never spread into it. `status` is one of `ok`, `drift`,
`conflict`, or `error`. Command-specific `data` is a documented discriminated
shape. Incompatible changes require `schemaVersion: 2`; field order, array
order, and map-to-array conversion are deterministic in version 1.
`summary` and diagnostic `message` are display text and must not be used as
machine discriminants; stable status, code, and typed data fields carry that
contract.

Diagnostics contain stable `code`, `severity`, `operation`, `domain`, optional
project-relative `path`, optional `archiveEntry`, optional `modelLocation`,
and a sanitized `message`. They contain no token, environment dump, absolute
path, original external archive path, username, hostname, stack, or arbitrary
exception serialization.

After `--json` is successfully parsed, stdout contains the envelope and stderr
is empty for expected success, drift, conflict, validation, and operational
outcomes. No progress text is emitted. Failures before output mode can be
established, such as malformed command syntax, retain the human stderr usage
error. Sanitized internal failures use an `error` envelope when JSON mode is
known. The envelope's `exitCode` always equals the process result.

Schema version 1 has not shipped in a released v0.2 package. TFSB24 therefore
finalizes, rather than migrates, that pre-release contract: reconciliation
records carry `plannedAction` and exact `requiredAuthority` domain fields.
Human `action` prose is display-only. A colliding new asset uses
`plannedAction: "blocked_collision"`, `requiredAuthority: "rename"`, and
`resolutionRequired: false`; it is not mislabeled as resolution authority.
Machine diagnostic severity is the closed value `error` because internal
diagnostics do not currently produce truthful warning or information states.

## Static preview gallery

`tfsb preview` parses and validates canonical state and freshly serializes SVGs.
It creates a static directory with `index.html`, `preview.css`, and an `assets/`
copy of the fresh SVG bytes. It does not inline input SVG into HTML, start a
server, launch Playwright, or require any browser package at runtime. Playwright
remains development-only qualification evidence.

Input-derived title, description, IDs, filenames, and status labels are inserted
only as HTML text after escaping `&`, `<`, `>`, `"`, and `'`. Asset URLs are
constructed from validated filenames with percent-encoded path segments. The
page has no script, remote resource, font, active embed, or companion rendering.
Every gallery image uses native `loading="lazy"` and `decoding="async"`; these
are inert browser hints and add no runtime code.
Companions are listed by filename and digest only. A fixed Content Security
Policy permits only same-directory images and styles.

The gallery renders canonical SVG state. Read-only build/install observations
appear as clearly labeled badges and never replace the image source. Missing or
unsafe derived state is labeled `missing`, `drift`, or `unavailable`, never
clean. Preview generation does not require clean build/install state.

Schema 1 has no favicon/mark/lockup taxonomy, so preview does not invent one.
It uses a deterministic geometry presentation profile:

- near-square view boxes (`0.8 <= width / height <= 1.25`) receive 16, 24, 32,
  48, 64, 128, and 256 pixel views;
- wide view boxes (`width / height > 1.25`) receive 160, 320, and 640 pixel
  width views; and
- tall view boxes receive 96, 192, and 384 pixel height views.

Every asset is also shown once on white, light gray, charcoal, black, and a
checkerboard transparency surface, with ID, filename, viewBox, title, and
description. This bounded geometry rule naturally gives Terminal Nova
favicons actual-size views and lockups useful widths without adding a schema
field or relying on filename heuristics. Preview refuses more than 128 assets
before staging so a hand-authored project cannot create unbounded gallery work.

The default output is `.tfsb-preview`, project-confined and disjoint from
canonical, build, and install paths. A bundle target is a per-invocation value,
not persistent project state, so preview planning cannot infer an unrelated
concurrent bundle target; an orchestrating caller that plans both must keep
their targets disjoint. To guarantee path safety and
prevent destination collision, `.tfsb-preview` is added to `PROTECTED_TREES`
in `src/root.ts`. Replacement is allowed only when the existing directory has a
valid `.tfsb-preview.json` marker whose fixed-order inventory and hashes match
the complete generated directory. The marker proves only directory ownership;
it never validates or approves canonical state. Preview acquires the shared
`.tfsb.lock`, writes and fsyncs a complete owner-only sibling stage, reparses
the staged marker, revalidates canonical and target snapshots, and then uses a
guarded backup/promotion/rollback sequence. The final identity-check-to-rename
race remains because portable Node filesystem APIs do not provide directory-fd
conditional replacement.

`--open` invokes `open`, `xdg-open`, or `explorer.exe` without a shell and with
the final `index.html` path as a separate argument, only after successful
generation. It is deterministically recorded as `skipped` in CI or another
noninteractive process. Opener failure is recorded as `failed`; neither state
changes successful generation into command failure. Opening does not affect the
zero-browser-runtime generation claim.

## Public library boundaries

The [typed v0.2 model sketch](../examples/v0.2/model.ts) separates:

- validated snapshots from untrusted archive/provenance decoding;
- pure reconciliation, diff, format, bundle, and preview planners;
- immutable plans from filesystem commit functions;
- command result values from human and JSON presenters; and
- canonical tree transactions from single-file and generated-directory
  transactions.

Public APIs return discriminated values and stable diagnostics. They do not
return CLI text, `parseArgs` objects, `fflate` objects, filesystem exceptions, or
internal class shapes. CLI rendering is a leaf adapter over public result
values.

## Cross-feature invariants

| Question | v0.2 rule |
| --- | --- |
| Is human TOML formatting semantic identity? | No. Parse, validate, and the versioned canonical semantic digest define identity. |
| Does formatting change provenance? | No. It can change raw build-receipt source hashes and therefore requires a later build for clean `check`. |
| What does bundle read? | Fresh canonical model and companion bytes only; build/install cleanliness is not required. |
| Can reconcile update provenance only? | Yes, for bootstrap matches, convergence, and explicit canonical resolutions. |
| What does preview render? | Fresh canonical SVG only; build/install state is labeled supplementary evidence. |
| How are renames represented? | Explicit mapping plus one canonical transaction; implicit absence is never a rename or deletion. |
| What does conflict do? | It blocks all apply writes and exits `2` until each conflict has an explicit direction. |
| How are multiple canonical writes committed? | Complete-tree staging, revalidation, swap, rollback, and recoverable residue diagnostics. |
| Does provenance validate an archive? | No. Current archive inspection, SVG parsing, companion allowlist, and hashes always run. |
| Does a bundle manifest validate bundle content? | No. Every named entry, digest, model, collision, and allowlist rule is checked independently. |

## Transaction and mutation model

Reconcile and `fmt` share the existing plan/stage/swap pattern at the canonical
tree boundary. The implementation must:

1. acquire an exclusive project-local mutation lock `.tfsb.lock` directly in
   the project root directory (sibling to `.tfsb/`, within the confined project
   root) without following a symlink;
2. snapshot canonical identities and bytes used by the plan;
3. create a unique same-parent staging tree with owner-only staging modes;
4. populate a complete allowlisted next `.tfsb` tree without following source
   symlinks, preserving unchanged companion bytes exactly;
5. fsync staged files and directories where supported;
6. revalidate confinement, canonical snapshot identity, and all proposed bytes;
7. rename current `.tfsb` to a unique backup, rename stage to `.tfsb`, and
   fsync the parent;
8. restore the backup on a handled commit failure; and
9. remove the backup only after the new tree is active.

No portable filesystem primitive makes a populated directory replacement and
power-loss recovery one indivisible operation. A crash may leave a uniquely
named stage or backup directory (`.tfsb-stage-*` or `.tfsb-backup-*`). To ensure
unambiguous recovery, project root discovery (`findProjectRoot`) checks for
these transaction markers in candidate directories before traversing upward. If
an orphan marker is present while `.tfsb/project.toml` is absent, normal commands
fail with a clear recovery diagnostic (`TFSB_RECOVERY_REQUIRED`) rather than
guessing or walking into ancestor directories. A cleanup failure after the new
tree is active is reported separately and does not silently roll back
successful canonical state. Promotion-durability diagnostics distinguish a
replacement whose backup remains from an initial absent-to-present promotion
whose new tree is active but has no prior backup. Backup cleanup and rollback
failures retain their own explicit residue diagnostics.

Bundle writes use a sibling temporary file plus exclusive create, fsync, and
rename. `--force` uses a backup/restore sequence and never follows a target
symlink. Preview writes a complete marked staging directory and may replace only
a directory carrying the matching TFSB-generated marker. TFSB24 deliberately
hardens the previously retained build/install contracts before v0.2 release:
their public inspection plans are frozen but carry no mutation authority;
authentic execution state is held privately, coordinated by the shared
canonical lock, and revalidates canonical, build-target/build-output, and
destination snapshots before replacement. Receipt, output, and destination
inspection requires bounded non-symlink regular files read through one opened
file snapshot. Receipt v2 remains valid ownership evidence. The final
identity-check-to-rename race is documented rather than described as portable
atomic no-replace behavior.

| Mutating command | Planned unit | Commit unit | Failure preservation |
| --- | --- | --- | --- |
| `import` | complete new `.tfsb` | absent-to-present directory rename | no canonical tree on failure |
| `reconcile --apply` | complete next `.tfsb` | canonical tree swap | old complete tree or recoverable residue |
| `fmt` | complete next `.tfsb` | canonical tree swap | old complete tree or recoverable residue |
| `build` | complete generated directory | generated tree swap | prior owned build restored or explicit rollback failure |
| `install` | all destination replacements | per-destination staged files with rollback | prior bytes restored where possible; partial state explicit |
| `bundle` | one complete ZIP | sibling file rename | prior target retained unless explicit force commit succeeds |
| `preview` | complete generated gallery | marked directory swap | prior marked gallery retained or explicit rollback failure |

Dry-run, `check`, `list`, and every `diff` mode are read-only.

## Command and exit-code matrix

Existing command meanings are unchanged. Exit `1` remains invalid input,
validation failure, unsafe filesystem state, or failed operation. Exit `2`
continues to mean valid but non-clean state for `check` and extends that same
meaning to new inspection/check commands. JSON distinguishes drift from
conflict.

| Command/outcome | Status | Exit | Mutation |
| --- | --- | ---: | --- |
| `import`, `build`, or `install` succeeds | `ok` | 0 | existing contract |
| Existing command validation/operation fails | `error` | 1 | existing rollback contract |
| `check` clean | `ok` | 0 | none |
| `check` valid with source/build/install drift | `drift` | 2 | none |
| `list` valid | `ok` | 0 | none |
| Reconcile inspection has no pending or conflicting state | `ok` | 0 | none |
| Reconcile inspection has changes, omissions, untracked records, or conflicts | `drift` or `conflict` | 2 | none |
| `reconcile --apply` completes all safe/explicit actions | `ok` | 0 | one canonical transaction |
| `reconcile --apply` has any unresolved conflict | `conflict` | 2 | none |
| Reconcile archive/provenance/path validation fails | `error` | 1 | none |
| `bundle --dry-run` or bundle write succeeds | `ok` | 0 | none or one output file |
| Diff equal | `ok` | 0 | none |
| Diff valid and different | `drift` | 2 | none |
| Requested diff baseline unavailable/invalid | `error` | 1 | none |
| `fmt --check` already canonical | `ok` | 0 | none |
| `fmt --check` needs formatting | `drift` | 2 | none |
| `fmt` succeeds | `ok` | 0 | one canonical transaction |
| Preview succeeds, including unavailable derived badges | `ok` | 0 | one generated directory |
| Any new command validation/commit fails | `error` | 1 | none or explicit rollback state |

## Security review

| Threat | Required control and failure mode |
| --- | --- |
| Malicious revised archive | Reuse complete central-directory validation, bounded reads, CRC verification, safe SVG parser, companion allowlist, and fail-before-plan behavior. |
| Archive entry collision or ambiguity | Portable NFC/case-folded key uniqueness, exact selectors, one-to-one explicit maps, and unresolvable collision errors. |
| Archive absence used as deletion | Omission is read-only status; only explicit per-record removal flags authorize canonical removal. |
| False clean/conflict | Paired checkpoints, versioned digest basis, current recomputation, explicit accepted divergence, deterministic classification tests. |
| Provenance staleness/tampering | Closed validation, path/ID cross-check, missing-record bootstrap rules, no authentication claim, never bypass canonical/archive validation. |
| Partial canonical write | Complete-tree plan/stage/reparse/swap, exclusive lock, rollback, and fail-closed recovery residue. |
| Symlink race/path escape | Existing real-root confinement, lstat/no-follow checks, same-parent staging, precommit recheck, and refusal on changed snapshot identity. |
| ZIP resource abuse | Existing archive count/size/ratio/ZIP64 bounds on import; bundle inputs already bounded canonical/companion state and precomputed output-size limits. |
| Bundle overwrite | Project-confined disjoint target, absent by default, no symlink target, explicit `--force`, sibling stage and rollback. |
| Bundle metadata leak | Fixed ZIP metadata; manifest allowlist; no TOML, provenance, receipt, absolute path, timestamp, host, or user. |
| JSON leakage | Deliberate DTOs, project-relative paths, normalized entry names, sanitized diagnostics, no object spreading or stacks. |
| Preview HTML injection | Fresh validated SVG files referenced as images, five-character HTML escaping, percent-encoded paths, fixed CSP, no input scripts/styles/URLs. |
| Companion active content | Companions are never rendered, parsed as markup, or linked for inline display; gallery lists only name and digest. |
| Unsafe preview replacement | Project-confined output and marker-authenticated directory swap; unknown directories are never cleared. |
| Stale build receipt mistaken for provenance | Separate kinds, locations, decoders, APIs, and status vocabulary; v2/v3 receipts are regenerated comparison evidence and neither reader accepts a provenance shape. |

## Verification strategy

Implementation phases must add focused executable evidence for:

- every classification row, bootstrap state, accepted divergence, convergence,
  explicit resolution direction, omission, collision, and rename;
- injected failures before staging, during staging, before swap, after backup,
  during rollback, and during cleanup;
- pinned `fflate` headers, entry order, attributes, absence of metadata, two
  repeated bundle byte comparisons, and timezone-independent fixed DOS fields;
- bundle manifest hash verification and semantic round-trip of the production
  SVG/README selection;
- typed gradient, presentation, transform, metadata, and path changes;
- formatter semantic equality, multi-file transaction failure, and expected
  post-format `check` source drift;
- JSON schema fixtures, deterministic ordering, exit/envelope parity, and
  absolute-path/secret leakage rejection; and
- preview escaping, CSP, no scripts or remote URLs, companion non-rendering,
  geometry profiles, marked replacement, and static file loading. Playwright
  may verify generated output only in development tests.
